# Контракт Technology

`Technology` — воспроизводимый технический подход с определёнными функцией,
отличительным механизмом и границей понятия. Новизна и число источников не
являются условиями создания. Никакого списка разрешённых технологий нет.
Рейтинг, признаки слабого сигнала и формулы отбора этим изменением не меняются.

## Обработка и хранение

1. Extractor возвращает исходные имена в `LocalEntity.evidence` и отдельно
   `LocalEntity.technology`: `canonical_name`, `definition`, `function`,
   `mechanism`, `boundary`, `identity_scope`, `evidence`. У цитат определения
   есть `supports_fields`; несколько предложений и фрагментов одного источника
   могут поддерживать одно определение. Каноническое имя не обязано быть
   дословным. Результаты испытаний и стадии остаются отдельными утверждениями.
2. Reviewer проверяет сущности в `Review.entity_items`, включая сущности без
   claims. Решения: `accept`, `reclassify`, `unresolved`. Для Technology нужны
   поддержка всех полей и положительные проверки конкретности, связности,
   самостоятельного подхода/адаптации и отсутствия результатов в определении.
   Общая область, длинное название, бренд или применение в новой отрасли
   не заменяют технический механизм. ML разрешается по контексту.
3. `assess_entity` проверяет решение, дословность, видимость и адреса цитат.
   Отсутствующая проверка Technology, несовместимые решения, неполное описание
   и внешние фрагменты оставляют `ConceptCandidate` с причиной. Исходное
   предложение сохраняется в `ProcessingRun.metadata.entity_proposals`.
   Исправленный тип повторно проверяется против типов ролей claims.
4. `EntityAssessment` сохраняется в `ExtractionResult`, `Mention` и Neo4j:
   `ProcessingRun-[:ASSESSED_ENTITY]->EntityAssessment-[:EVIDENCE_IN]->Chunk`.
   `payload_json` хранит полное решение, цитаты и происхождение. Связь `MENTIONS`
   содержит `assessment_id`. Предыдущие решения сохраняются у своих запусков.
5. `Concept.technology` содержит `TechnologyProfile` версии `technology/1`:
   описание, цитаты с интервалами, ID документа и запуска, причину проверки.
   Neo4j хранит его как `technology_json`; `definition`, `preferred_label`,
   `identity_scope`, исходные `names_json` и стабильный `concept_id` доступны
   отдельно. Запись Technology без проверенного профиля запрещена.
6. `read_concepts` восстанавливает профиль; temporal reader и `/api/search`
   передают его в дополнительном поле `technologyDefinition`. Это не меняет
   состав формул рейтинга. Старые узлы читаются с пустым профилем: чтение не
   означает, что они прошли новый контракт.

Старый плоский `profile` сохраняется для совместимости читателей. Для принятой
Technology его `classification_status = validated` теперь выводится из
независимого решения, а не только из заполненных строк. Прежние плоские ответы
без нового досье сохраняются как предложения и требуют повторного извлечения.
Флаги старого контракта, длина полей и форма сокращений не заменяют эту проверку.
Отдельный короткий triage заменён этой же проверкой по полным фрагментам;
старый список имён продуктов не используется для назначения типов.
Заголовки остаются контекстом пакетов; chunks с цитатами определения сохраняются
даже при режиме хранения только доказательных фрагментов.

## Разрешение идентичности

Проверенная сущность получает ID из точного типа, нормализованного канонического
имени и проверенного смысла `identity_scope` (`concept-v3`). Неразрешённый смысл
ограничивается текущим документом. Старый алиас не может автоматически привязать
новое определение к прежнему ML. Варианты регистра, пунктуации и словоформ
нормализуются; расшифровка сокращения должна исходить из текста. Принятые имена
после явно выполненного объединения сохраняют ID целевого узла.

Одиночная разметка больше не повышает Method/Material до Technology ни в resolver,
ни при записи, ни при объединении. Конфликт сохранённых типов останавливает запись
с предложением повторной обработки. Связи `belongs_to_domain` и
`subtechnology_of` остаются отдельными проверяемыми утверждениями. Старая
миграция ключей не объединяет разные типы и пропускает новые смысловые профили.
Вакансии и гранты также проходят полный разбор: совпадение известного имени
не заменяет проверку контекста и не скрывает новые подходы в том же документе.
Ручное назначение типа Technology без проверенного профиля запрещено.
Низкоуровневый лексический resolver по-прежнему умеет читать старые предложения;
созданное им имя Technology без профиля нельзя опубликовать через GraphStore.

## Безопасная повторная обработка

Команда принимает локальный JSON-снимок. Она не создаёт GraphStore, не подключается
к Neo4j и не имеет флага `--apply`:

```sh
python -m lctrend technology-dry-run \
  --input snapshot.json --output technology-plan.json
```

Формат входа:

```json
{
  "documents": [{
    "document": {"...": "полный DocumentEnvelope с исходными chunks"},
    "previous_result": {"...": "предыдущее ExtractionResult, необязательно"},
    "answers": [{"...": "Extractor"}, {"...": "Reviewer"}]
  }]
}
```

`answers` используется только с `--replay`. Без этого флага работает настроенный
провайдер извлечения и проверки. Путь вывода не может совпадать с входом.
Предыдущий результат должен принадлежать соответствующей версии документа.

Отчёт содержит полный `original_snapshot`, новые результаты, причины и цитаты,
изменения по документам и общий `identity_plan`. Сопоставление старых и новых
сущностей использует пересечение адресов исходных упоминаний. Несколько новых
смыслов одного старого ID дают предложение `split`, а отсутствие свидетельств —
`needs_context`. Не генерируются удаления, команды применения или замена
исходных документов. Перед отдельной миграцией нужен полный снимок всех
источников затронутых узлов; частичный снимок не обосновывает глобальное слияние.

## Проверка и примеры

Контрольная выборка находится в `tests/fixtures/technology_contract.json`.
Она включает реальный собранный абстракт The Definition of Standard ML
(OpenAlex snapshot), а остальные фрагменты явно помечены как репрезентативные.
Таблица из задания прочитана как источник уровня конкретности: использованы
направления строк 6, 11 и 12 (сигналы 4, 9, 10). Её оценки, стадии и названия
не импортировались в рабочий граф. FIS-ML в положительном примере — специально
заданное тестовое сокращение, а не утверждение о реальной публикации.

Сравнение выполнено с кодом ревизии
`2d15228506b6f6c86f107e300966981d8490e7bd`, на одинаковых предложениях Extractor.
Изменение объединено с последующим `origin/main` (`24f0d96`); сохранены
новые экономические контракты, параллельная обработка и слой рейтинга.
Reviewer в исходном коде проверял только claims. В новом коде воспроизводятся
заранее подготовленные решения сущностей. Итог: 15/15 запусков успешны;
6 конкретных подходов приняты, 2 области и 1 компания переклассифицированы,
6 случаев оставлены кандидатами. Полнота на шести подготовленных положительных
случаях — 6/6; ошибочных Technology на девяти отрицательных — 0/9.
Это показатели контрольного воспроизведения, а не качества живой модели.

| Исходный фрагмент | Прежний результат | Новый результат |
| --- | --- | --- |
| CNN: общие обучаемые ядра скользят по локальным пикселям | Technology по имени CNN, без определения | Technology «Convolutional neural network» с функцией, механизмом и цитатами |
| Vision Transformer: патчи, позиционные представления, self-attention | Technology по имени | Technology с прослеживаемым определением из нескольких предложений |
| cache tiering: неактивные KV-блоки копируются в DRAM и восстанавливаются по запросу | Technology с общим именем | Technology «Request-indexed KV cache offload to host DRAM» |
| Machine learning (ML) is a research field | Technology ML | Domain «Machine learning» |
| Standard ML is a general-purpose programming language… | Technology ML | ConceptCandidate ML: установлен контекст языка, технического механизма в абстракте недостаточно |
| We used Python to plot the results | Technology Python | ConceptCandidate: назван инструмент |
| FIS-ML с определённым механизмом формирования импульса / FIS-ML без расшифровки | Один и тот же Technology ID | Technology / отдельный ConceptCandidate |

Dry run предложил 6 замен старой идентичности с сохранением типа и 9
переклассификаций. Общий план обнаружил разделение прежних ML и FIS-ML по
свидетельствам разных документов. Краткий машинный отчёт:
[`technology-contract-check.json`](technology-contract-check.json).
Полный локальный отчёт с сохранёнными входами создавался за пределами репозитория
в `../technology-contract-check/dry-run.json`; живой граф не читался и не менялся.

Дополнительные тесты проверяют варианты имён и омонимы, несколько фрагментов
одного источника, одиночный достаточный источник, неполные поля, выдуманные и
внешние цитаты, неподтверждённую комбинацию, отраслевое переименование,
противоречащие решения и одинаковые решения с разными объяснениями, запись/чтение
Neo4j-параметров, запрет автоматического повышения типа, сохранение исходного
снимка и неизменность оценок поиска при добавлении определения.

Проверки: `pytest` — 1194 passed, 1 skipped; `ruff check src tests` — успешно;
`git diff --check` — успешно. Тесты записи используют контролируемую транзакцию,
без живой Neo4j. Провайдер модели в окружении не настроен: независимый прогон
извлечения и семантической проверки живой моделью не выполнялся. Её ошибки,
покрытие источников, лимиты контекста и неодинаковая канонизация смысловых
синонимов остаются ограничениями; неизвестные случаи не превращаются в
проверенную Technology по одному имени.
