# Часть 0. Термины, что берём из кода, раскладка файлов

## 0.1 Термины

| Термин | Значение |
|---|---|
| **T, срез** | дата, на которую считаем всё. Видно только то, что опубликовано или наблюдалось до T включительно (`TemporalCorpus.view(T)`). |
| **Строка** | пара «технология × T». Единица обучения. |
| **Корень** | технология, для которой строится подграф и делается прогноз. |
| **Реестр** | ~1000 технологий, прошедших «врача» (LLM-триаж) и проверку поискового запроса. На них учим. |
| **Глобальный ряд** | годовые счётчики работ, организаций, репозиториев по технологии из внешних API (OpenAlex, GitHub), а не из нашего графа. Из них считаются **метки**. |
| **Состояние** | `insufficient / weak / trend / mature / faded` на дату T. |
| **`signal_36m`** | главная метка: на T технология была настоящим ранним сигналом (потом стала трендом или выжила нишей), а не шумом и не мейнстримом. |
| **`trend_36m`** | вспомогательная метка: переход в тренд подтвердился в (T, T+36 мес.]. |
| **Расширитель** | узел, через который сэмплер идёт на следующий шаг (документ, конкретная технология, небольшая организация). |
| **Лист (терминальный узел)** | узел, который попадает в подграф, но через который дальше **не идём**: хабы (крупные организации, общие технологии, обзоры) и задачи. |
| **Якорь** | сущность, которая **не становится узлом вообще**, а кодируется признаком у документа или технологии: страна (США, Китай …), домен, источник, автор. |

Правило, которое снимает проблему «огромного числа точек»: **США, «машинное обучение», Google и обзор на 150 технологий не должны быть мостами между технологиями.** Через них связано всё со всем, и сообщение, прошедшее через такой узел, — шум. Поэтому страна, домен, источник и автор — якоря (признаки, а не узлы), а хабы — листья (узлы без продолжения). Подробно — часть 6.

# Часть 2. Этап 1 — реестр технологий («очередь к врачу»)

**Цель:** ~1000 конкретных технологий с надёжным поисковым запросом, среди них и победители, и ниши, и затухшие.

### Шаг 1.1. Кандидаты из графа

**Вход:** Neo4j.

**Что сделать.** Cypher (в `registry/queue.py`):

```cypher
MATCH (t:Technology)
WHERE t.kind IN ['Technology', 'Method']
OPTIONAL MATCH (t)<-[:MENTIONS]-(:Chunk)<-[:HAS_CHUNK]-(v:DocumentVersion)
WITH t, count(DISTINCT v) AS documents
WHERE documents >= $min_documents
RETURN t.concept_id AS concept_id, t.preferred_label AS label,
       t.definition AS definition, t.names_json AS names_json,
       documents
ORDER BY documents DESC
```

Отбросить: метки из `ranking.json → candidates.generic_labels`; `taxonomy_general_term = true` на последнем срезе.

**Выход:** `artifacts/registry/candidates_graph.jsonl`, одна строка:
`{"concept_id", "label", "definition", "synonyms": [...], "documents", "origin": "graph"}`.

**Параметры:** `registry.min_documents = 3`.

### Шаг 1.2. Семена от LLM

**Зачем.** Граф собран сегодняшними запросами и видит в основном то, что известно сейчас. Если учить только на нём, модель не увидит технологий, которые не взлетели.

**Что сделать.** 11 областей (`ranking.json → signals.areas` без «Другое») × 5 эпох (2000, 2005, 2010, 2015, 2020) = 55 вызовов GigaChat 2 Pro. Промпт `prompts/seeds.txt`:

```
Область: {area}. Год: {year}.
Назови 20 конкретных технологий, которые в {year} году были на ранней стадии:
были публикации, прототипы или пилоты, но не было массового внедрения.
Ровно 10 из них должны быть технологиями, которые позже НЕ получили широкого
распространения (затухли или остались узкой нишей).
Не называй области и общие слова (ИИ, IoT, блокчейн вообще, большие данные).
Технология = механизм + объект + сценарий.
Для каждой верни JSON-объект:
{"canonical_en": "...", "name_ru": "...", "synonyms_en": ["...", "..."],
 "mechanism": "одно предложение", "later_outcome_guess": "spread|niche|faded"}
Ответ — JSON-массив из 20 объектов, без текста вокруг.
```

**Важно.** `later_outcome_guess` — **только** для балансировки очереди (шаг 1.7). В метки не идёт никогда: это знание современной модели о будущем.

**Выход:** `artifacts/registry/seeds.jsonl`, поля те же + `area`, `seed_year`, `origin: "seed"`.

### Шаг 1.3. Слияние и дедупликация

**Что сделать.**
1. Для каждого семени считаем ключ резолвера (`extraction/lexical.identity_key`) по `canonical_en` и всем синонимам. Совпал с концептом графа → семя становится синонимом концепта (`origin: "graph+seed"`).
2. Эмбеддинг `canonical_en: mechanism` (та же модель, что `Concept.embedding_text`). Косинус ≥ 0.90 с кандидатом → тот же объект.
3. Остальные семена — новые кандидаты без `concept_id` (получат его, когда появятся документы).

**Выход:** `artifacts/registry/queue.jsonl` — очередь, порядок: сначала `graph+seed`, затем `graph` по числу документов, затем `seed`.

### Шаг 1.4. «Врач» (LLM-триаж)

**Вход:** строка очереди + досье из графа (если есть `concept_id`): до 5 документов по годам (год, заголовок, тип), 3 цитаты упоминаний, свидетельства зрелости со стадией.

**Модель:** GigaChat 2 Lite; если `is_technology` и `niche_specific` расходятся с правилом генерических меток или ответ невалиден — повтор на Pro. Каждый вызов и выбор модели пишется в лог (`llm/stats.py`) — ТЗ требует раскрывать выбор модели.

**Промпт `prompts/triage.txt`:**

```
Ты проверяешь, является ли объект конкретной технологией для реестра.
Объект: {label}. Определение: {definition}. Синонимы: {synonyms}.
Досье: {dossier}

Ответь JSON:
{"is_technology": bool,        // механизм/метод/материал/устройство, а не область, продукт-бренд, задача или организация
 "niche_specific": bool,       // достаточно узкое, чтобы по нему искать (не "AI", не "cloud")
 "canonical_en": str,
 "name_ru": str,
 "synonyms_en": [str],         // 1–5 вариантов для поиска, без общих слов
 "exclude_terms": [str],       // слова, отсекающие омонимы ("island" для Java)
 "area": str,                  // строго одно из: {areas}
 "parent": str | null,         // более общая технология
 "reason": str}                // одно предложение
Не оценивай, стала ли технология успешной.
```

**Выход:** `artifacts/registry/triage.jsonl`.

### Шаг 1.5. Проверка поискового запроса

**Зачем.** Метки считаются по счётчикам OpenAlex. Если запрос «Transformer» ловит трансформаторы подстанций, ряд испорчен, и метка будет ложной.

**Что сделать.**
1. Запрос: `search=` синонимы через ` OR ` в кавычках; `exclude_terms` — через `NOT`. (Синтаксис булевого поиска OpenAlex проверить на 5 примерах до массового запуска.)
2. `works?search=…&sample=10&seed=13&select=title,publication_year` → 10 заголовков.
3. Промпт `prompts/precision.txt`: «Технология: {canonical_en} — {mechanism}. Для каждого заголовка ответь 1, если работа об этой технологии или её применении, иначе 0. JSON-массив из 10 чисел».
4. Если единиц < 7: одна попытка — попросить у LLM уточнённые `synonyms_en`/`exclude_terms` и повторить; иначе `rejected: ambiguous`.
5. Заодно `works?search=…` → `meta.count` (всего работ).

**Выход:** `artifacts/registry/precision.jsonl`: `{"key", "query", "precision", "total_works", "attempt"}`.

### Шаг 1.6. Решение о приёме

| Условие | Статус |
|---|---|
| `is_technology = false` | `rejected: not_technology` |
| `niche_specific = false` | `rejected: generic` |
| точность запроса < 0.7 после уточнения | `rejected: ambiguous` |
| `total_works` < 10 | `rejected: too_rare` |
| косинус ≥ 0.90 с уже принятой | `rejected: duplicate` (+ синоним принятой) |
| иначе | `accepted` |

**Выход:** `artifacts/registry/registry.jsonl`:

```json
{"registry_id": "reg:000123", "concept_id": "tech:…" , "status": "accepted",
 "reject_reason": null, "canonical_en": "federated learning",
 "name_ru": "федеративное обучение", "synonyms_en": ["federated learning"],
 "exclude_terms": [], "query": "\"federated learning\"", "precision": 0.9,
 "total_works": 18450, "area": "Инфраструктура ИИ", "parent": "machine learning",
 "origin": "graph+seed", "seed_year": 2015, "outcome_guess": "spread"}
```

В граф: `SET t.registry_status, t.registry_id, t.registry_area` для технологий с `concept_id`. Отклонённые с причинами `generic`/`not_technology` — отрицательные примеры для `signal_36m` (часть 4.5).

### Шаг 1.7. Состав очереди и балансировка

Идём по очереди, пока принятых не станет 1000. Контроль состава по `outcome_guess` (только для балансировки): если доля `faded` среди принятых < 20%, следующие 100 мест отдаём семенам с `faded`. Итоговую долю затухших по **меткам** (часть 4) проверяем после этапа 3; если < 20% — добираем семена.

### Шаг 1.8. Пилот с ручной разметкой

**До** обработки всей тысячи:
1. 100 технологий: 50 из графа, 50 семян, по всем 11 областям.
2. Для каждой — 3 случайные даты из сетки (часть 4.1).
3. Двое независимо ставят состояние (`insufficient / weak / trend / mature / faded`) по графику глобального ряда (этап 2) и свидетельствам зрелости, по инструкции ниже. Файл `pilot_annotations.csv`: `registry_id, T, annotator, state, comment`.
4. Каппа Коэна по 300 парам. ≥ 0.6 — идём дальше. Ниже — разбор расхождений, правка инструкции, повтор на 30 новых.
5. На этой же разметке подбираем пороги части 4.3 (сетка значений, максимум согласия правила с разметкой). **Пороги фиксируются и больше не меняются** — ни по valid, ни по test.

Инструкция для разметчика (одна страница):
> Технология — механизм + объект + сценарий. На дату T смотрите только на график до T и свидетельства до T. **Слабый сигнал** — есть проверяемые публикации/прототипы от ≥ 2 независимых групп, но доля в области мала и массового внедрения нет. **Тренд** — доля заметная (в верхних 10% технологий области), растёт, ≥ 5 организаций в год, держится год. **Зрелая** — массовое внедрение или 3+ года после тренда. **Затухла** — была слабым сигналом, но 2 года нет новых организаций и доля упала вдвое от пика. **Мало данных** — < 3 работ за 2 года.

**Проверка этапа 1:** `registry.jsonl` содержит ≥ 1000 `accepted`, у каждой точность запроса ≥ 0.7; каппа пилота ≥ 0.6; распределение по областям — ни одна не больше 20%.

# Часть 3. Этап 2 — глобальные ряды

**Цель:** для каждой технологии реестра — полные годовые ряды 1990–2026, не зависящие от того, что мы успели скачать. Из них считаются метки.

**Почему не наш граф.** Граф собран запросами сегодняшнего дня: в 2005 году в нём есть только то, что связано с сегодняшними темами. Отсюда нынешняя проблема E-2: отрицательную метку нельзя поставить, потому что нельзя доказать, что «ничего не было». Агрегаты OpenAlex видят всё.

### Шаг 2.1. Подполе технологии (для знаменателя)

`works?search=<query>&group_by=primary_topic.subfield.id` → подполе с наибольшим числом работ. Записать `subfield_id`, `subfield_share` (доля работ технологии в этом подполе). Если доля < 0.3 — технология междисциплинарная: знаменатель = `field` (уровень выше), флаг `broad_denominator = true`.

### Шаг 2.2. Ряды

| Ряд | Запрос | Когда | Вызовов на технологию |
|---|---|---|---|
| `works[y]` | `works?search=<query>&group_by=publication_year` | всегда | 1 |
| `field_works[y]` | `works?filter=primary_topic.subfield.id:<id>&group_by=publication_year` | один раз на подполе (общий кэш `series/subfields/`) | 0 |
| `orgs[y]` — список id институтов | `works?search=<query>&filter=publication_year:<y>&group_by=authorships.institutions.id` (до 200 групп) | годы от первой работы − 1 до 2026 | ~15 в среднем |
| `repos[y]` | GitHub `search/repositories?q=<synonym> created:<y>-01-01..<y>-12-31` → `total_count` | годы ≥ 2008 | ≤ 19 |
| `patents[y]` | EPO OPS, счётчик по году приоритета | если доступ к OPS настроен | ≤ 37 |

Для организаций храним **идентификаторы** (до 200 в год), не только число: нужны «новые организации» — те, что не встречались раньше. У технологии, где организаций в год больше 200, фаза слабого сигнала уже прошла, точное число там не важно — пишем `orgs_truncated = true`.

**Бюджет.** ~35 вызовов OpenAlex на технологию × 1000 ≈ 35 тыс. при суточном лимите 100 тыс. (polite pool, `OPENALEX_MAILTO`), 10 запросов/с. GitHub search — 30 запросов/мин с токеном: 1000 × ~15 ≈ 15 тыс. запросов ≈ 8 часов, запускать на ночь, с возобновлением.

### Шаг 2.3. Формат кэша

`artifacts/series/<registry_id>.json`:

```json
{"registry_id": "reg:000123", "query": "\"federated learning\"",
 "fetched_at": "2026-09-30", "subfield_id": 1702, "broad_denominator": false,
 "works": {"2015": 3, "2016": 41, "2017": 180},
 "orgs": {"2016": ["I123", "I456"], "2017": ["I123", "I789", "…"]},
 "orgs_truncated": {"2021": true},
 "repos": {"2016": 2, "2017": 35},
 "patents": null}
```

### Шаг 2.4. Годовые ряды → окна на любую дату T

Сетка срезов квартальная с 2015 года, а ряды годовые. Окно «последние 12 месяцев до T» считаем пропорцией:

```
window(series, T, 12) = Σ_y series[y] · overlap_months((T−12, T], год y) / 12
```

Для T = 2020-04-01: 9/12 от 2019 года + 3/12 от 2020 года. Это приближение (внутри года считаем равномерно), точность — квартал. Если нужна точнее — `group_by=publication_date` в пределах 2 лет вокруг перехода, только для технологий, у которых переход попал в этот интервал.

Производные на T:

| Величина | Формула |
|---|---|
| `share(T)` | `window(works, T) / window(field_works, T)` |
| `share_growth(T)` | `log((window(works,T)+1)/(window(field,T)+1)) − log((window(works,T−12)+1)/(window(field,T−12)+1))` |
| `orgs_12m(T)` | число различных id в `orgs` за годы, пересекающие окно (с весом по доле окна: организация из года, покрытого на 3/12, считается, только если год покрыт ≥ 6 мес.; иначе берём предыдущий полный год) |
| `new_orgs(a, b)` | id, появившиеся в (a, b] и не встречавшиеся до a |
| `share_pct(T)` | перцентиль `share(T)` среди технологий реестра **того же подполя** на T |
| `families(T)` | число семейств с ≥ 1 записью в окне: работы, репозитории, патенты |

### Шаг 2.5. Догрузка документов реестра в граф (без LLM)

Выполняется **после этапа 3** (состояния считаются только по рядам, граф им не нужен), потому что ей нужна `trend_confirmed_date`.

**Зачем.** Метки считаются по глобальным рядам, а **признаки** — по нашему графу. Технология-семя, которой нет в графе, признаков не имеет, и учиться на ней нельзя. Документы нужно догрузить, но прогнать 100+ тыс. документов через LLM-извлечение невозможно (десятки секунд на документ). Поэтому догрузка идёт **без LLM**.

**Что сделать** (`registry/backfill.py`, команда `lctrend registry-backfill`):
1. Для каждой принятой технологии: `works?search=<query>&filter=publication_year:<y>&sort=cited_by_count:desc&per_page=50` по каждому году от первой работы до `min(2026, trend_confirmed_date + 3 года)`; не больше 50 работ в год. В слабой фазе работ мало (обычно < 20 в год), поэтому она попадает почти целиком; обрезка по 50 касается уже трендовых лет. Такие годы помечаются `sampled_year = true`.
2. Работа идёт через существующий адаптер `parse_openalex` → `DocumentEnvelope` (метаданные, аннотация, организации, страны, домены, топики) и запись `GraphStore.write_processed` в режиме `none` (без извлечения).
3. Упоминания без LLM: `linking/names.py` ищет в заголовке и аннотации названия **всех** технологий реестра (по ключу резолвера, синонимы реестра добавлены как принятые имена). Найденное → `MENTIONS {method: "registry_name", resolution_status: "accepted", observed_at: дата публикации}`. Технология, по запросу которой пришла работа, получает упоминание, даже если в аннотации стоит синоним, который лексический поиск не поймал (`method: "registry_query"`). **Внимание:** режим `none` сейчас не пишет чанки (`graph.json → chunk_nodes_note`), а `MENTIONS` идёт от `:Chunk`. Нужна новая запись `GraphStore.write_registry_mentions(version, chunk, technology_ids)`: чанк заголовка+аннотации становится узлом (он «несёт упоминание», это согласуется с `chunk_nodes = "evidence"`), от него — `MENTIONS`.
4. GitHub — по той же схеме: до 20 репозиториев на технологию, отсортированных по дате создания, `parse_github`, без LLM.
5. **По желанию, если есть квота:** для 5 самых цитируемых работ слабой фазы каждой технологии — обычное LLM-извлечение только по аннотации (1 пакет, GigaChat Lite). Даёт свидетельства зрелости и отношения (`DEVELOPED_BY`, `USED_BY`), которых без LLM нет. Около 5000 вызовов.

**Что это значит для признаков.** Признаки, которые требуют LLM (зрелость, утверждения, отношения из текста, экономика из текста), у большинства исторических строк будут пустыми — это пропуск с маской, а не ноль. Признаки масштаба и структуры (документы, организации, страны, независимость, совместные упоминания) есть у всех. Счётчики в годы `sampled_year` занижены — поэтому масштаб модель берёт из глобальных рядов (признаки `g_*`, часть 5.3), а из графа — структуру.

**Бюджет:** 1000 технологий × ~3 страницы = ~3 тыс. вызовов OpenAlex; ~100–150 тыс. работ в граф. Запись — ночь, с возобновлением по `CrawlRun`.

**Проверка этапа 2:** у ≥ 95% принятых технологий есть `works` и `orgs`; выборочно 20 технологий — график глазами (нет ли провала из-за неверного запроса); у ≥ 90% принятых технологий в графе ≥ 3 документа слабой фазы.

## 4.3 Состояния на дату T

Функция `labels/states.py → state_at(series, maturity_events, registry_row, T) -> State`. Проверки идут **строго в этом порядке**, первое сработавшее — результат:

| # | Состояние | Условие | Стартовый порог |
|---|---|---|---|
| 1 | `rejected` | статус реестра не `accepted` | — |
| 2 | `mature` | `max_maturity_rank(≤T) ≥ 6` (`mass_adoption`) **или** `T ≥ trend_confirmed_date + 36 мес.` | 6; 36 мес. |
| 3 | `trend` | `T ≥ trend_confirmed_date` | — |
| 4 | `faded` | `faded_date` определена и `T ≥ faded_date` | — |
| 5 | `insufficient` | `window(works, T, 24) < 3` **или** ряд обязательного для эпохи семейства не получен (сбой или нет доступа к API) — речь о полноте наблюдения, а не о том, нашлись ли записи | 3 |
| 6 | `weak` | ≥ 2 организаций за 24 мес. **и** `max_maturity_rank(≤T) ≤ 5` или неизвестна | 2; 5 |
| 7 | `insufficient` | всё остальное (например, 1 организация) | — |

Даты перехода считаются один раз на технологию, проходом по сетке:

**`first_threshold_date`** — первая дата T, где одновременно:
- **масштаб:** `share_pct(T) ≥ 0.90` **и** `window(works, T, 12) ≥ 20`;
- **рост:** `share_growth(T) ≥ log(1.5)`;
- **независимость:** `orgs_12m(T) ≥ 5` **и** `families(T) ≥ 2`.

**`trend_confirmed_date`** — первая дата T, где условия выше выполнены на T **и на всех датах сетки в [T − 12 мес., T]**, причём таких дат ≥ 2. В годовой эпохе это T и T−12; в квартальной — 5 дат подряд. Рост на всех датах окна не требуем — достаточно на первой и последней (иначе один провальный квартал обнуляет год роста).

**`faded_date`** — первая дата T после хотя бы одного `weak`, где:
- за 24 мес. до T нет ни одной **новой** организации (`new_orgs(T−24, T) = ∅`), **и**
- `share(T) < 0.5 · max(share(t) для t ≤ T)`.

После `faded_date` технология может «воскреснуть»: если позже снова выполняется условие `weak` с ≥ 3 новыми организациями за 12 мес. — `faded_date` сбрасывается, это пишется в `revived = true`. Для меток воскрешение до конца горизонта означает «ниша выжила».

Точность дат: `year` для T до 2004, `half` для 2005–2014, `quarter` с 2015.

**Выход:** `artifacts/labels/states.parquet`:

| registry_id | concept_id | T | state | share | share_pct | share_growth | orgs_12m | families | max_stage |
|---|---|---|---|---|---|---|---|---|---|

и `artifacts/labels/transitions.parquet`: `registry_id, first_threshold_date, trend_confirmed_date, faded_date, revived, date_precision`.

### Ответ на вопрос «а если все условия держатся долго»

Держатся долго — значит, тренд подтверждён с первой даты, когда они продержались 12 месяцев. Всё, что после, — `trend`, а через 36 мес. — `mature`. Обратно в `weak` технология не возвращается, даже если рост замедлился: замедление после тренда — это зрелость. Слабая фаза — от первых двух организаций до `trend_confirmed_date`; она может длиться 10 лет, и каждая дата в ней — отдельная строка выборки.

## 4.4 Почему метку нельзя поставить по состоянию на ту же дату

Если бы метка была просто `state(T) == weak`, она считалась бы по тем же числам на T, что и признаки. Модель восстановила бы правило, точность вышла бы около 100% — и ничего бы не значила. ТЗ требует другого: отделить **значимые** ранние индикаторы от **шума** и от **зрелого**. Значим ли сигнал, видно только по тому, что было потом. Поэтому метка смотрит вперёд от T, признаки — только назад.

## 4.5 Метки

`labels/labels.py → build_labels(states, transitions, registry, data_end)`.

`data_end = 2026-07-01` (последняя дата сетки). Горизонт `H = 36 мес.`

**`signal_36m`** — для всех технологий реестра (включая отклонённые) на всех датах сетки:

| Значение | Условие | `label_reason` |
|---|---|---|
| 1 | `state(T) = weak` **и** (`trend_confirmed_date ∈ (T, T+H]` **или** `state(T+H) = mature`) | `became_trend` |
| 1 | `state(T) = weak` **и** ниша выжила: `|new_orgs(T, T+H)| ≥ 2` **и** `share(T+H) ≥ 0.5 · share(T)` **и** `state(T+H) ≠ faded` | `niche_survived` |
| 0 | `state(T) = weak` **и** `state(T+H) = faded` или (новых организаций < 2 и доля упала больше чем вдвое) | `faded` |
| 0 | `state(T) ∈ {trend, mature}` | `mainstream` |
| 0 | `status ∈ {rejected: generic, rejected: not_technology}` и есть `concept_id` — на тех T, где у концепта в нашем графе ≥ 3 документов за 24 мес. | `not_signal` |
| null | `state(T) = weak`, но исход смешанный (новые организации есть, а доля упала вдвое, или наоборот) | `ambiguous_outcome` |
| null | `state(T) = insufficient` | `insufficient` |
| null | `T + H > data_end` (T > 2023-07-01) — для всех строк, включая мейнстрим, чтобы последние годы не состояли из одних нулей | `horizon_open` |

| Значение | Условие |
|---|---|
| 1 | `trend_confirmed_date ∈ (T, T+H]` |

**Выход:** `artifacts/labels/labels.parquet`:

| registry_id | concept_id | T | state | signal_36m | signal_reason | trend_36m | horizon_end |
|---|---|---|---|---|---|---|---|

**Проверки этапа 3 (тесты `tests/labels/`):**
1. Синтетический ряд «рост 3 года → держится» → `trend_confirmed_date` ровно через 12 мес. после первого выполнения.
2. «Один провальный квартал внутри года роста» → подтверждение не сдвигается.

6. Ни одна строка с `state = insufficient` не получила 0/1.

## 5.2 Расчёт


## 5.5 Автоматическая чистка на train

Порядок фиксирован, результат пишется в `feature_list.json` с причиной для каждого выкинутого:
1. Пропусков > 95% строк train → выкинуть.
2. Одно значение у ≥ 99% строк → выкинуть.
3. Пары со |Спирмен| > 0.95 → выкинуть ту, что стоит **дальше** в списке 5.3.
4. Всё. Отбор по важности модели не делаем: он подгоняет список под valid.

## 5.6 Преобразования

`model/tech_features.py → fit_transform(train_rows)`: для каждого признака по train — `clip_lo = P1`, `clip_hi = P99`, после log — `mean`, `std`. Сохраняется в `artifacts/features/transform.json`. Применение к любой строке:

```
v = row[name]
if v is None or not finite: out = 0.0; mask = 1
else:
    v = clip(v, clip_lo, clip_hi)
    if transform == "log": v = log1p(max(v, 0))
    if transform == "yrs": v = log1p(v / 365.25)
    if transform in ("log", "yrs", "z"): v = (v - mean) / (std or 1)
    # pct и b — как есть; pct центрируем: v - 0.5
    out = v; mask = 0
```

# Часть 6. Этап 5 — граф среза: какие узлы есть, какие не расширяются, что в векторе каждого узла

## 6.1 Четыре роли сущностей

Главная проблема графа для HGT — **хабы**. США связаны с половиной документов, «машинное обучение» — с половиной технологий, Google — с сотнями. Если идти через них, в двух шагах от любой технологии оказывается весь граф, а сообщения, пришедшие через хаб, одинаковы для всех и ничего не различают. Поэтому у каждой сущности графа — одна из четырёх ролей:

| Роль | Что значит | Кто |
|---|---|---|
| **Узел-расширитель** | в подграфе, через него идём на следующий шаг | обычная технология, документ (не обзор), небольшая организация |
| **Узел-лист** | в подграфе, но дальше через него **не идём**; его вектор содержит «я хаб» и свою степень | крупная организация, общая технология, обзорный документ (для технологий), задача |
| **Якорь (признак)** | **не узел**; превращается в несколько чисел в векторе документа или организации | страна, домен, источник, автор, язык |
| **Исключено** | не узел и не признак подграфа; его смысл уже свёрнут в признаки технологии (часть 5) | чанки, утверждения, свидетельства зрелости и экономики, экономические факты, узлы таксономии, служебные узлы |

| Тип | Хаб, если | Примеры | Что происходит |

| `org` | `tech_count(T)` — число разных технологий, связанных с организацией через документы или отношения, ≥ **max(50, P99 организаций на T)** | Google, MIT, Академия наук КНР, Siemens | лист: попадает в подграф как соседка, но её другие технологии не берём |
| `tech` | метка в `generic_labels` **или** `taxonomy_general_term = true` **или** реестр `rejected: generic` **или** `document_count(T)` ≥ P99.5 технологий на T и ≥ 500 | «deep learning», «neural networks», «IoT» | лист, если это сосед; если это **корень** — расширяется как обычно (корень всегда центр) |

| `task` | всегда | «classification», «anomaly detection» | всегда лист |

Почему хабы не выбрасываем совсем: «разрабатывает Google» и «разрабатывает стартап из 3 человек» — разные сигналы. Хаб как лист передаёт ровно это: кто рядом, насколько он крупный. Но через него не приходят сообщения от сотен чужих технологий.

На каждой дате в лог пишется: число хабов по типам, доля рёбер, касающихся хабов. Если хабов-организаций > 2% — порог слишком низкий, поднять.

| 8 | (`org`, `rev_affiliated`, `doc`) | обратное | |

| 12–14 | (`org`, `rev_developed_by` / `rev_used_by` / `rev_funded_by`, `tech`) | обратные | |
| 15 | (`tech`, `solves`, `task`) | `SOLVES` | |

**Корзины возраста (1–6) заменяют временное кодирование HGT.** В оригинальной статье HGT есть относительное временное кодирование, в `HGTConv` из PyG его нет. Три корзины дают модели то же: у «свежих» и «старых» документов разные веса внимания, и рост внимания виден как перевес свежей корзины. Одно и то же упоминание на T = 2019 — `recent`, на T = 2021 — `mid`; поэтому граф строится **на каждую дату отдельно**.

Видимость: ребро и оба его узла видны на T (`event_visible`, `first_visible ≤ T`, у отношений `observed ≤ T`).

## 6.8 Сборка графа среза

`model/hetero.py → build_snapshot_graph(corpus, T, features_T, registry, config) -> SnapshotGraph`:

1. `view = corpus.view(T)`.
2. **Узлы `tech`:** все `view.technologies` + цели `SUBTECHNOLOGY_OF` и `SIMILAR_TO`, у которых нет документов (им — все признаки пустые + маски). Вектор — из `features/<T>.parquet` через `transform.json`.
3. **Узлы `doc`:** объединение `DocumentTrace.document_id` всех технологий (одно произведение — один узел). Вектор 6.4.
4. **Узлы `org`:** участники документов + цели `DEVELOPED_BY/USED_BY/FUNDED_BY`. Вектор 6.5.
5. **Узлы `task`:** цели `SOLVES`. Вектор 6.6.
6. **Хабы** по 6.3; флаги `is_hub`, `is_survey`, `is_consortium` пишутся и в вектор, и в отдельные булевы массивы (их читает сэмплер).
7. **Рёбра** 19 типов, с корзинами относительно T.
8. **Сохранение** `artifacts/hgt/snapshots/<T>.pt`:

```python
{
  "T": "2016-01-01",
  "x": {"tech": float16[N_tech, D_tech], "doc": float16[N_doc, 57],
        "org": float16[N_org, 22], "task": float16[N_task, 20]},
  "ids": {"tech": [concept_id...], "doc": [work_id...], "org": [...], "task": [...]},
  "flags": {"tech_hub": bool[N_tech], "doc_survey": bool[N_doc],
            "doc_consortium": bool[N_doc], "org_hub": bool[N_org]},
  "doc_meta": {"reliability": int8[N_doc], "fulltext": bool[N_doc], "date": int32[N_doc]},
  "edges": {("tech","mentioned_recent","doc"): int32[2, E], ...},   # 19 типов
  "edge_time": {("tech","mentioned_recent","doc"): int32[E], ...}, # дни от 1970
  "edge_attr": {("tech","similar_to","tech"): float16[E]},         # косинус, для порядка в сэмплере
  "feature_names": {"tech": [...], "doc": [...], "org": [...], "task": [...]}
}
```

`doc_meta` нужен сэмплеру для порядка выбора документов (часть 7).

**Размер.** На поздней дате: ~150 тыс. `doc` × 57 + ~20 тыс. `tech` × ~140 + ~50 тыс. `org` × 22 ≈ 13 млн чисел ≈ 26 МБ в `float16`. 82 даты — ~1–1.5 ГБ на диске, ранние даты много меньше. В память — одна-две даты одновременно (кэш LRU на 4 даты).

**Проверки этапа 5 (`tests/model/test_hetero.py`):**
1. Ни одного узла и ребра с датой > T.
2. Документ, добавленный с датой T + 1 день, не меняет файл среза T.
3. Упоминание с датой T − 6 мес. — в `mentioned_recent`, T − 24 мес. — `mentioned_mid`, T − 5 лет — `mentioned_old`.
4. Организация с 60 технологиями при P99 = 40 — хаб; с 30 — нет.
5. Узлов типов `Country`, `Domain`, `Source`, `Author` нет; в векторе `doc` сумма `region_*` ≥ 1.
6. `feature_names` совпадают с `feature_list.json`; нет колонок `future_*`, `label_*`.

# Часть 7. Этап 6 — сэмплер подграфа: сколько соседей у каждой точки

**Цель:** для корня r на дате T — подграф не больше 400 узлов, где у каждого типа соседей свой лимит, хабы не расширяются, выбор воспроизводим.

`model/sampler.py → sample(G_T, root, seed, config) -> Subgraph`. Заменяет BFS из `subgraphs.py`.

## 7.1 Почему нынешний BFS не подходит

`subgraphs.py:284–305`: на каждом шаге для **каждой** вершины и **каждого** типа ребра берётся до `max_neighbors = 30` соседей, а типы рёбер перебираются по алфавиту. У документа сначала идут `ASSOCIATED_WITH` и `CONTRIBUTED_BY` (до 30 авторов), и только потом `IN_DOMAIN` и `MENTIONED_IN`. Лимит `max_nodes = 400` выбирается авторами первых 10–20 документов, а соседние технологии и домены остальных документов в подграф не попадают. Какие документы успеют — определяет алфавитный порядок id, а не время и не надёжность.

## 7.2 Лимиты

**Шаг 1 — от корня.** Корень расширяется всегда, даже если он сам хаб.

| Ребро | Лимит | Порядок выбора внутри типа |
|---|---|---|
| `mentioned_recent` | 12 | надёжность ↓, полный текст ↓, `hash(seed, root, doc)` |
| `mentioned_mid` | 10 | то же |
| `mentioned_old` | 10 | то же |
| `developed_by` | 10 | дата ребра ↓ (свежие первыми), hash |
| `used_by` | 10 | то же |
| `funded_by` | 5 | то же |
| `solves` | 8 | hash |
| `subtech_of` (родители) | 3 | не-хабы первыми, hash |
| `parent_of` (дочерние) | 7 | не-хабы первыми, hash |
| `similar_to` | 8 | косинус ↓ (нужно сохранить `cosine` как атрибут ребра в файле среза) |
| **максимум** | **83** | |

Недобор в корзине **не переносится** в другую: если свежих документов 2, берём 2, а не добиваем старыми. Пустая свежая корзина — это и есть сигнал затухания.

**Шаг 2 — только от расширителей шага 1.**

| От кого (шаг 1) | Условие расширения | Куда | Лимит на каждый | Порядок | Максимум |
|---|---|---|---|---|---|
| `doc` (32) | не `is_survey` | другие `tech` (любая корзина) | 3 | не-хабы первыми, hash | 96 |
| `doc` (32) | не `is_consortium` | `org` (`affiliated`) | 3 | не-хабы первыми, hash | 96 |
| `tech` через `subtech_of` / `parent_of` / `similar_to` (18) | не хаб | `doc` | 3 | дата ↓ | 54 |
| `org` через роли (25) | не хаб | другие `tech` (`rev_developed_by` / `rev_used_by` / `rev_funded_by`) | 2 | hash | 50 |
| `task` | никогда | — | 0 | — | 0 |
| **максимум шага 2** | | | | | **296** |

**Итого максимум:** 1 + 83 + 296 = **380** узлов, потолок `max_nodes = 400`. На практике — 150–250: у технологии в слабой фазе мало документов и отношений.

**Если потолок превышен** (при изменённых лимитах): узлы шага 2 удаляются в порядке `task` → `org` → `doc` → `tech`, внутри типа — по hash. Узлы шага 1 не удаляются никогда.

**Третьего шага нет.** HGT — 2 слоя, сообщение с третьего шага до корня не дойдёт.

## 7.3 Алгоритм

```
sample(G_T, root, seed):
    selected = {("tech", root)}
    hop1 = []
    for edge_type, limit, order in HOP1_RULES:
        cand = [n for n in neighbors(G_T, ("tech", root), edge_type) if n not in selected]
        for n in sorted(cand, key=order(seed, root))[:limit]:
            selected.add(n); hop1.append((n, edge_type))
    hop2 = []
    for n, via in hop1:                               # порядок hop1 фиксирован
        for edge_type, limit, order, condition in HOP2_RULES[type(n), via]:
            if not condition(G_T, n):                 # хаб / обзор / консорциум / задача
                continue
            cand = [m for m in neighbors(G_T, n, edge_type) if m not in selected]
            for m in sorted(cand, key=order(seed, root))[:limit]:
                selected.add(m); hop2.append(m)
    trim(hop2, max_nodes - 1 - len(hop1), priority=["tech", "doc", "org", "task"])
    edges = induced_edges(G_T, selected)              # ВСЕ рёбра 19 типов между выбранными
    return relabel(selected, edges, root_first=True)  # корень = локальный индекс 0 в "tech"
```

`hash(seed, root, node) = sha256(f"{seed}|{root}|{node}")` — как сейчас в `subgraphs.py`, выбор не зависит от порядка входных данных.

`induced_edges` берёт все рёбра между выбранными узлами, а не только дерево выборки: если два выбранных документа связаны с одной выбранной организацией, оба ребра попадают в подграф.

## 7.4 Варианты выборки

- **Обучение:** 4 варианта на корень (`seed = 0, 1, 2, 3`), эпоха `e` использует вариант `e mod 4`. Это аугментация: модель не запоминает конкретный набор документов.
- **Вывод:** 5 вариантов (`seed = 100…104`), вероятности усредняются. Разброс между вариантами — `p_signal_std`, показатель неустойчивости прогноза.
- Хранение: `artifacts/hgt/samples/<variant>.npz` — для каждого корня индексы узлов по типам в графе среза (int32) и смещения. ~30 тыс. корней × 4 варианта × 380 × 4 байта ≈ 180 МБ. Признаки не дублируются: они лежат один раз в файле среза.

## 7.5 Сборка батча

`model/dataset.py`:
1. Для корня: загрузить `snapshots/<T>.pt` (LRU-кэш на 4 даты), взять индексы из `samples/<variant>.npz`, вырезать `x` (float16 → float32), перенумеровать рёбра.
2. `HeteroData` на корень; корень — узел `tech` с локальным индексом 0.
3. `Batch.from_data_list(128 подграфов)`; индекс корня i-го подграфа в батче — `batch["tech"].ptr[i]`.
4. К батчу — `y_signal`, `y_trend`, `w_signal`, `w_trend`, `mask_signal`, `mask_trend` (часть 8).

**Проверки этапа 6 (`tests/model/test_sampler.py`):**
1. Одинаковый seed → одинаковый подграф; перестановка входных рёбер его не меняет.
2. Хаб-организация есть в подграфе, но ни одна технология, связанная только с ней, не попала.
3. Обзорный документ есть, но его остальные технологии не попали.
4. Ни одного узла `Country`, `Domain`, `Source`, `Author`.
5. У корня с 3 свежими и 100 старыми документами: свежих ровно 3, старых ровно 10.
6. Размер ≤ 400 на 1000 случайных корнях; распределение размеров — в отчёт.

# Часть 8. Этап 7 — обучающая выборка: корни, веса, разбиения

## 8.1 Корни

Корень = строка `labels.parquet` с `signal_36m ∈ {0, 1}`, у которой технология есть в графе на T (есть узел `tech` в файле среза). Нет узла → строка выбрасывается с причиной `no_graph_node` (счётчик — в отчёт: если таких > 20%, догрузка шага 2.5 недостаточна).

`trend_36m` у корня есть, только если `state(T) = weak` и горизонт закрыт; иначе `mask_trend = 0`.

## 8.2 Веса

1. **Каждая технология весит 1 в своей задаче:** `w = 1 / n_строк(технология, задача)`. Иначе технология с 40 квартальными строками перевесит 15 годовых.
2. **Мейнстрим ×0.5:** строки с `signal_reason = mainstream` умножаются на 0.5. Их отсекает и прозрачное правило (часть 14), но модель должна давать им низкую вероятность на датасете организаторов.
3. **Балансировка эпоха × класс:** эпохи — 1990–2004, 2005–2014, 2015+. Для каждой клетки (эпоха, класс) — сумма весов `W[e, c]`; множитель `f[e, c] = (Σ W / число клеток) / W[e, c]`, обрезан в [0.2, 5]. Иначе модель выучит «много пропусков = старые годы = класс такой-то».
4. Веса нормируются так, чтобы средний вес строки train = 1.

## 8.3 Разбиение по времени

| Часть | Срезы T | Горизонт кончается не позже |
|---|---|---|
| train | ≤ 2013-01-01 | 2016-01-01 |
| purged (не используется) | 2013-07-01 … 2015-10-01 | — |
| valid | 2016-01-01 … 2018-01-01 | 2021-01-01 |
| test | 2021-01-01 … 2023-07-01 | 2026-07-01 |
| refit перед test | ≤ 2018-01-01 | 2021-01-01 |

Если в train < 3000 размеченных строк (мало ранней истории), сдвиг: train ≤ 2015-01-01, valid 2018-01-01 … 2019-07-01, test 2022-07-01 … 2023-07-01 — записать выбранный вариант в отчёт **до** первого прогона на test.

## 8.4 Разбиение по технологиям

# Часть 10. Этап 9 — HGT: архитектура, обучение, калибровка, выбор

## 10.1 Архитектура

```python
class SignalHGT(nn.Module):
    def __init__(self, in_dims, metadata, tab_dim, hidden=64, heads=4, layers=2, dropout=0.2):
        super().__init__()
        self.inp = nn.ModuleDict({t: nn.Linear(d, hidden) for t, d in in_dims.items()})
        self.convs = nn.ModuleList(HGTConv(hidden, hidden, metadata, heads) for _ in range(layers))
        self.tab = nn.Sequential(nn.Linear(tab_dim, 32), nn.ReLU(), nn.Dropout(dropout))
        self.head = nn.Sequential(nn.Linear(hidden + 32, 32), nn.ReLU(),
                                  nn.Dropout(dropout), nn.Linear(32, 2))
        self.dropout = dropout

    def forward(self, batch):
        h = {t: F.gelu(self.inp[t](batch[t].x)) for t in batch.node_types}
        for conv in self.convs:
            out = conv(h, batch.edge_index_dict)
            h = {t: F.dropout(out[t] if out.get(t) is not None else h[t],
                              self.dropout, self.training) for t in h}
        roots = batch["tech"].ptr[:-1]                 # корень — локальный 0
        z = torch.cat([h["tech"][roots], self.tab(batch["tech"].x[roots])], dim=1)
        return self.head(z)                            # [B, 2]: signal, trend
```

| Что | Размер |
|---|---|
| Вход `tech` | ~120–150 → 64 |
| Вход `doc` | 57 → 64 |
| Вход `org` | 22 → 64 |
| Вход `task` | 20 → 64 |
| `HGTConv` × 2 | 64 → 64, 4 головы по 16; в `HGTConv` PyG уже есть остаточная связь с обучаемым затвором |
| Табличный обход | вектор корня → 32 |
| Голова | 96 → 32 → 2 |
| Параметров | ~150–250 тыс. |

**Табличный обход** — прямая дорога от признаков корня к голове. Если граф ничего не добавит, модель опирается на неё и не проигрывает baseline по построению.

## 10.2 Функция потерь

```python
logits = model(batch)
l_sig = F.binary_cross_entropy_with_logits(logits[:, 0], y_signal, reduction="none")
l_trd = F.binary_cross_entropy_with_logits(logits[:, 1], y_trend, reduction="none")
loss = (l_sig * w_signal).sum() / w_signal.sum().clamp(min=1e-6) \
     + 0.5 * (l_trd * w_trend * mask_trend).sum() / (w_trend * mask_trend).sum().clamp(min=1e-6)
```

## 10.3 Обучение

| Параметр | Значение |
|---|---|
| Оптимизатор | AdamW, lr 1e-3, weight_decay 1e-4 |
| Батч | 128 корней |
| Эпох | до 60; ранняя остановка по PR-AUC `signal_36m` на valid, терпение 10 |
| Обрезка градиента | норма 1.0 |
| Варианты выборки | эпоха `e` — вариант `e mod 4` |
| Повторы | 5 seed: 13, 17, 19, 23, 29; отчёт — среднее ± стандартное отклонение |
| Железо | CPU; ~235 батчей на эпоху, ожидаемо 1–2 мин на эпоху |
| Лог | каждую эпоху: loss train, PR-AUC и ROC-AUC valid по обеим головам |

Refit перед test: train + valid строки со срезами ≤ 2018-01-01 (группы train + valid), столько эпох, сколько дала ранняя остановка.

## 10.4 Калибровка

«Уверенность модели 80%» из ТЗ должна означать: среди прогнозов около 0.8 примерно 80% — сигналы.

1. На valid подбираем температуру `τ` для каждой головы: минимум взвешенного log-loss от `sigmoid(logit / τ)` (LBFGS, одна переменная).
2. Если valid ≥ 2000 строк и после температуры ECE > 0.05 — изотоническая регрессия поверх.
3. Отчёт: ECE по 10 корзинам (взвешенный) и диаграмма надёжности до/после.
4. Сохранение: `artifacts/models/calibration.json`.

Порог «слабый сигнал / нет» для метрик accuracy и F1 — **0.5 после калибровки**. Второй порог (максимум accuracy на valid) — только для датасета организаторов, если их метрика — accuracy; оба числа в отчёт.

## 10.5 Абляции (на valid, 3 seed)

| Вариант | Что проверяем |
|---|---|
| HGT без табличного обхода | сколько даёт само сообщение по графу |
| HGT без `similar_to` | вклад похожих технологий |
| HGT без корзины `mentioned_old` | нужна ли глубокая история |
| HGT с якорями как узлами (`country`, `domain` — листья) | правильно ли решение «якорь, а не узел» |
| HGT с `Author` как листьями | нужны ли авторы узлами |
| HGT, 1 слой | нужен ли второй шаг |

## 10.6 Выбор модели для выдачи

HGT идёт в выдачу, если **одновременно**:
- средний PR-AUC `signal_36m` на valid (5 seed) выше лучшего CatBoost на ≥ 0.02;
- ECE после калибровки не хуже CatBoost больше чем на 0.02.

Иначе в выдачу идёт CatBoost, HGT — слайд «исследование», с цифрами абляций. Решение принимается на valid и записывается в `report.json` **до** прогона test.

**Выход:** `hgt_<seed>.pt`, `calibration.json`, `report.json` (метрики всех моделей на valid и test-наборах, абляции, выбор).

# Часть 12. Этап 11 — поисковый индекс BM25F + вектор

**Цель:** по запросу за доли секунды находить технологии графа, подходящие по смыслу, на любом языке запроса.

## 12.1 Что индексируем

Один «документ» индекса = **карточка технологии**, а не статья: выдача ТЗ — технологии. В индекс — все `tech` с ≥ 1 документом.

| Поле | Откуда | Вес поля `w_f` | `b_f` |
|---|---|---|---|
| `label` | `preferred_label` | 3.0 | 0.3 |
| `aliases` | принятые имена (`names_json`), синонимы реестра, `name_ru` | 3.0 | 0.3 |
| `definition` | `Concept.definition` | 2.0 | 0.75 |
| `tasks` | метки целей `SOLVES` | 1.5 | 0.75 |
| `domains` | `BELONGS_TO_DOMAIN`, домены документов (названия каталога), `area` реестра | 1.5 | 0.75 |
| `parents` | метки целей `SUBTECHNOLOGY_OF` | 1.0 | 0.75 |
| `quotes` | до 3 цитат упоминаний и утверждений (`evidence_quotes`) | 1.0 | 0.75 |
| `titles` | заголовки 5 последних документов | 0.5 | 0.75 |

`b = 0.3` у коротких полей: длина названия почти ничего не говорит о релевантности.

## 12.2 Токенизация (`search/tokenize.py`)

1. NFKC, casefold, `ё → е`.
2. Токены — `[\w+#]+` (C++, C# остаются целыми).
3. Аббревиатура — токен, который в исходном тексте был весь в верхнем регистре и не длиннее 5 символов (LLM, RAG, MCP, ИИ): не стеммируется.
4. Остальное — стемминг Snowball: кириллица → русский, латиница → английский (`snowballstemmer` уже в зависимостях).
5. Стоп-слова документов: стандартные короткие списки RU/EN (предлоги, союзы, артикли).
6. **Стоп-слова запроса** (дополнительно): `технология, технологии, решение, решения, перспективный, перспективные, слабый, слабые, сигнал, сигналы, тренд, тренды, новый, новые, область, области, сфера, направление, в, для, по, emerging, technology, technologies, trend, trends, weak, signals, new, solutions, field`.

Запросы из ТЗ после очистки: «технологии в ИИ» → `ии`; «перспективные решения в финтехе» → `финтех`; «слабые сигналы в области кибербезопасности» → `кибербезопасн`.

## 12.3 BM25F

Для термина q и технологии d:

```
tf~(q, d) = Σ_f  w_f · tf_f(q, d) / (1 − b_f + b_f · len_f(d) / avglen_f)
score(q, d) = IDF(q) · tf~ · (k1 + 1) / (tf~ + k1)
IDF(q)      = ln(1 + (N − df(q) + 0.5) / (df(q) + 0.5))
BM25(Q, d)  = Σ_{q ∈ Q} weight(q) · score(q, d)
```

`k1 = 1.2`. `weight(q)` = 1 для слов запроса, 0.5 для расширений (13.2).

Реализация — своя, ~60 строк на словарях: `index[term] = [(doc_idx, tf_label, tf_aliases, …)]`, `len_f`, `avglen_f`, `df`. При 1–20 тыс. карточек индекс строится за секунды. Библиотека не нужна; Neo4j fulltext тоже не подходит: он есть только для `Chunk.text` и `Document.title`.

## 12.4 Векторная часть

- Вектор технологии: `Concept.embedding` («название: определение»), нормированный.
- Матрица `float32 [N, dim]` в памяти, поиск — `matrix @ q` в numpy.
- Вектор запроса — **той же** моделью эмбеддингов, иначе косинусы несравнимы.

## 12.5 Хранение и обновление

`artifacts/search/index.pkl`: `ids`, поля, инвертированный индекс, матрица векторов, `tau` (13.4). Пересобирается вместе с полным скорингом (часть 11); после живого догруза новые технологии дописываются в индекс (без пересборки IDF — пересчёт ночью). `SearchService` загружает индекс вместе с кэшем графа.

## 13.2 Перевод и расширение (1 вызов LLM)

GigaChat 2 Lite, промпт `prompts/query.txt`:

```
Пользователь ищет зарождающиеся технологии. Запрос: «{query}».
Верни JSON:
{"ru": "суть запроса по-русски, 1–5 слов",
 "en": "то же по-английски, как это называют в научных статьях",
 "expansions_en": ["до 5 более узких англоязычных терминов этой области"],
 "domains": ["названия из списка: {catalog_domains}"]}
Не добавляй названия конкретных технологий, которых нет в запросе.
```

Кэш по нормализованному запросу (`artifacts/search/query_cache.json`). При сбое LLM — только исходный запрос + `match_domains` (уже есть в `search.py:75`).

## 13.3 Два списка и слияние

1. **BM25:** термины `ru` и `en` (вес 1) + `expansions_en` (вес 0.5) → топ-100.
2. **Вектор:** `max(cos(emb(en), d), cos(emb(ru), d))` → топ-100.
3. **RRF:** `RRF(d) = Σ_i 1 / (60 + rank_i(d))`; нет в списке — нет слагаемого.
4. **Бонус домена:** технология, у которой домен совпал с `domains` из 13.2 или `match_domains`, получает `+ 0.5 / 61`.
5. **Пул** — первые 200 по RRF.

## 13.4 Порог релевантности

RRF — порядок, не мера. Технология остаётся в пуле, если выполнено хотя бы одно:
- `cos ≥ τ`;
- `BM25 ≥ 0.5 · max BM25` этого запроса;
- совпал домен.

**Как получить τ:** 200 запросов (названия 11 областей, их синонимы и 150 названий технологий реестра) × 200 случайных технологий **из других областей** → косинусы → `τ = P95`. Так порог не зависит от шкалы конкретной модели эмбеддингов. Пересчитывается при смене модели эмбеддингов. Позже уточняется на 20 размеченных запросах (часть 16): τ, при котором доля нерелевантных в ТОП-15 ≤ 10%.

## 13.5 Когда своих кандидатов мало — живой догруз

ТЗ: поиск «не ограничен стартовым датасетом». Условие: после порога и фильтра мейнстрима (14.1) осталось < 30 технологий.

1. Задание `JobManager` (веб) / команда CLI:
   - OpenAlex: `search=<en>`, `from_publication_date = сегодня − 3 года`, по релевантности, 150 работ;
   - GitHub: `<en> created:>сегодня−3 года`, по звёздам, 50 репозиториев;
   - патенты — если OPS настроен.
2. Извлечение: только аннотация / README, один пакет, GigaChat Lite, параллельно 8 (пул ключей). ~200 вызовов, 2–4 минуты.
3. Новые концепты → эмбеддинги → дописываются в индекс (12.5).
4. Частичный пересчёт признаков и скоров (часть 11).
5. Повтор поиска.

Интерфейс: сразу показывает то, что есть, с пометкой «предварительно, идёт догрузка источников», и обновляет выдачу по завершении задания.

## 14.4 Объяснение прогноза

По ТЗ модель обязана показывать, **по каким признакам** наблюдение отнесено к сигналу. Три уровня, все считаются по **одному** выбранному варианту подграфа корня (seed 100).

**1. Признаки корня — Integrated Gradients (`captum.attr.IntegratedGradients`).**
- Функция: подграф фиксирован, меняется только вектор корня `x_root` (он входит и в `inp["tech"]`, и в табличный обход); выход — логит `signal`.
- Опорная точка: медиана train по каждому признаку (в преобразованном виде), маски = 0.
- 32 шага.
- Вклад признака = вклад значения + вклад его маски.
- Перевод в «процентные пункты»: `вклад_i_пп = attr_i / Σ attr · (p(x) − p(опоры))` — сумма вкладов равна разнице вероятностей. Это пропорциональное разнесение, а не точное разложение вероятности; так и подписываем.
- Показ: `label_ru` из `feature_list.json`, значение признака в исходных единицах («документов за 12 мес.: 14»), знак.

**2. Группы соседей — выключение.** Из подграфа убираются рёбра одной группы, замеряется Δp:

| Группа | Что убираем |
|---|---|
| свежие документы | `mentioned_recent` и обратные |
| документы 1–3 года | `mentioned_mid` |
| старые документы | `mentioned_old` |
| организации-разработчики и пользователи | `developed_by`, `used_by`, `funded_by` |
| похожие технологии | `similar_to` |
| родители и дочерние | `subtech_of`, `parent_of` |
| задачи | `solves` |

**3. Документы — выключение по одному.** До 32 документов корня, Δp для каждого; 3 с наибольшим падением p — «ключевые источники», с цитатами (`evidence_quotes`).

Стоимость: 15 карточек × (32 + 7 + IG 32) прогонов маленькой модели — секунды на CPU.

**Проверка честности объяснений (на valid, в отчёт):** удаляем k признаков с наибольшим вкладом (заменой на опору) — p должна падать быстрее, чем при удалении k случайных; кривая для k = 1…10.

**Чего не делаем:** не показываем веса внимания HGT как объяснение — разные распределения внимания могут давать одинаковый прогноз.

Для CatBoost (если выбран он): уровни 1 — SHAP, 2 и 3 — не применимы (соседей нет), вместо 3 — документы с наибольшим вкладом в признаки из топа (`evidence_quotes`).

## 14.5 Источники

Для каждого: название, ссылка, дата публикации, тип, **язык оригинала**, доверие. Для зарубежного — русское резюме (LLM) с пометкой «автоматический перевод», оригинальное название сохраняется.

Шкала доверия (явная, вместо нынешнего `tier / tier_max`, при котором патенты получают «низкое»):

| Доверие | Типы |
|---|---|
| высокое | научные публикации (OpenAlex), патенты (EPO), государственные реестры грантов (NIH, NSF), стандарты, регуляторные документы |
| среднее | репозитории, пакеты, аналитические отчёты, вакансии |
| низкое | новости, пресс-релизы, блоги, соцсети, агрегаторы |

Технология, у которой все источники «низкие», в ТОП не идёт (правило `hype`, 14.1) — прямое требование ТЗ.
