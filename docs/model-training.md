# Разметка и обучение модели слабого сигнала

Основание: приложенное ТЗ «Газпромбанк.Тех» и план в `md.md`. Целевая
метка — **был ли кандидат значимым ранним сигналом на дату среза**,
подтверждённым дальнейшей историей. Размечаются два отдельных исхода:
`signal_12m` и `signal_36m`. Отсутствие подтверждения за год не отменяет
возможного подтверждения за три года. Это не существующий
`label_realized`: тот означает первое наблюдаемое внедрение и остаётся
вспомогательным исходом. Нельзя размечать сигнал по тем же порогам роста,
которые попадут в признаки, и нельзя записывать отсутствие результата как
ноль при неполном наблюдении источников.

## 1. Экспертный пилот

```bash
python -m lctrend.modeling pilot \
  --technologies 100 \
  --output artifacts/review.csv
```

Команда только читает Neo4j через настроенные `NEO4J_URI`,
`NEO4J_USER`, `NEO4J_PASSWORD`. Получатся `review.reviewer_1.csv`,
`review.reviewer_2.csv` и `review.manifest.json`: два независимых бланка
примерно по три исторические даты на технологию. Даты: годовые до 2005,
полугодовые в 2005–2014, квартальные с 2015; срез имеет завершённый
годовой горизонт, но трёхлетний может быть ещё не завершён. Бланк показывает
документы и участников, датированных не позже среза. Но без `--as-known`
ретроспективная выгрузка может включать материал, найденный системой позже
этой даты. Для честного прогноза «как было известно тогда» нужны
`--as-known` и исторические даты получения; текущие 300 строк — пилот
разметки, не доказанный real-time backtest.

Разметчики независимо заполняют `reviewer_state` (`weak`, `trend`, `mature`,
`faded`, `insufficient`, `rejected`), отдельно `reviewer_signal_12m` и
`reviewer_signal_36m`, а также, если применимо, `reviewer_trend_12m` и
`reviewer_trend_36m` (`0`, `1` или пусто). Ноль означает проверенный
отрицательный исход именно за указанный срок, а не отсутствие записи в
графе. В `evidence_notes` приводят
проверяемые идентификаторы источников и обоснование. Если будущий исход
неясен или охват источников недостаточен, метка остаётся пустой. Перед
массовой разметкой сравнивают согласие экспертов, разрешают расхождения и
фиксируют определения. Родительские связи уже объединяются в семейства;
семантические почти-дубликаты проверяются вручную до разделения выборки.

Датасет организаторов из 100 сигналов сентября 2026 года — внешний
положительный пример для проверки смысла «слабого сигнала», но не источник
отрицательных меток и не историческая обучающая выборка: для него ещё не
прошёл даже один год наблюдения.

## 2. Проверенные метки и разбиение

Для пилота достаточно выгрузить признаки и подграфы отобранных срезов.
Новый двухгоризонтный бланк создавайте под другим именем, чтобы сохранить
прежние 168 строк:

```bash
python -m lctrend.modeling pilot \
  --technologies 100 --output artifacts/review-two-horizons.csv
```

```bash
python -m lctrend.modeling export-pilot \
  --review artifacts/review-two-horizons.reviewer_1.csv \
  --output artifacts/history-two-horizons.csv \
  --subgraphs artifacts/history-two-horizons.jsonl
```

Для массовой разметки выгружается весь текущий граф. Здесь нет ограничения
по числу технологий или трёх дат на каждую: используется вся историческая
сетка от самой ранней даты до конца корпуса, включая последнюю дату вне
сетки. Достаточно одного документа; технологии без видимого документа
остаются в отдельном инвентаре, а не получают выдуманные признаки.

```bash
python -m lctrend.modeling export-full \
  --output artifacts/full-history.csv \
  --review artifacts/full-review.csv \
  --subgraphs artifacts/full-subgraphs.jsonl
```

CSV содержит пустые экспертные метки и календарные флаги завершения 12/36
месяцев. Флаги не доказывают полноту исторических источников. Команда также
создаёт два независимых бланка, инвентарь технологий и манифест с числом
срезов и потенциальным когортным разбиением по каждому горизонту.

Две рецензии объединяются, а спорные строки остаются без метки до
адъюдикации. Дополнительный CSV для адъюдикации имеет поля
`technology_id,snapshot_date,signal_12m,trend_12m,signal_36m,trend_36m,adjudicator,reason`.

```bash
python -m lctrend.modeling prepare \
  --dataset artifacts/history-two-horizons.csv \
  --review-1 artifacts/review-two-horizons.reviewer_1.csv \
  --review-2 artifacts/review-two-horizons.reviewer_2.csv \
  --data-end YYYY-MM-DD \
  --output artifacts/labels.csv
```

`--data-end` — последняя **проверенная** дата наблюдения, не сегодняшняя
дата по умолчанию. Срез с более поздним концом горизонта остаётся без
метки. Для строгой временной проверки трёхлетнего исхода окна остаются:
обучение до 2013 года, валидация 2016–2018, тест 2021 — середина 2023.
Для годового исхода: обучение до 2020, валидация 2022, тест 2024 — середина
2025. Пересекающиеся горизонты отбрасываются. Одно семейство технологий не
попадает в несколько частей. Промежутки между ними не используются.

Альтернатива для **пилотной** оценки — пять фиксированных складок по
`family_id`. В каждой итерации одна складка служит валидацией, четыре —
обучением; другие даты той же семьи не перескакивают между ними. Это
позволяет использовать срезы из временных промежутков, но измеряет перенос
на другие технологии, **не** прогноз на будущие годы. Пять отчётов нужно
рассматривать вместе; финальный временной тест отдельно. До публикации
метрик нужно
проверить семантические родственные технологии, не покрытые явными
родительскими связями.

Ещё один вариант — динамическое **когортное** разбиение 80/10/10. Для каждой
семьи берётся год её первого появления; границы годов подбираются без
просмотра меток так, чтобы число строк было как можно ближе к 80%, 10% и
10%. Семьи и целые годы не разрываются. На старом пилоте границы получились
2020 и 2021 годы: 135 строк train, 21 valid, 12 test. При новой выгрузке
границы пересчитаются; их нужно сохранять вместе с версией набора данных.
Это проверка переноса на **новые когорты технологий**, но не строгий
point-in-time тест: поздний срез старой технологии может оказаться в train
позже раннего среза новой технологии в test. Для заявления о прогнозировании
будущего остаётся необходим отдельный временной тест.

Новый бланк `review-two-horizons` сформирован на графе 29 сентября 2026:
300 срезов 100 технологий (96 семейств). Календарно годовой горизонт
завершён у всех 300, трёхлетний — у 112. Для годовой задачи динамические
границы дают 249/21/30 строк train/valid/test; для трёхлетней — 92/12/8
из 112 пригодных по календарю. Это **потенциальные** строки: исходы ещё не
размечены и полнота источников не доказана.

Текущий граф содержит документы, но при аудите не было записей `CrawlRun`
о полном охвате источников. Поэтому автоматические отрицательные метки
`label_realized` невозможны, а вручную проставленные нули требуют
проверяемого объяснения и независимой второй рецензии. В частности,
нельзя обучать модель, называя все технологии без будущего патента
«не сигналом».

### Что получилось на текущем удалённом графе

Пилот реально выгружен в `artifacts/` 29 сентября 2026 года: 56 технологий,
168 исторических срезов, 184 исходных столбца признаков и компактные
двухшаговые подграфы. Из 168 срезов 163 имеют только научные статьи,
3 — только код, 2 — сочетание кода и статей; патентной конвергенции здесь
ещё нет. Доказательства зрелости представлены только в 17 срезах.
Разметочные поля намеренно пусты. С учётом трёхлетнего горизонта и
разделения по времени потенциально остаются всего 2 строки train и
2 valid (ещё 80 — test, 83 вне окон и 1 пересекает границу горизонта).
Таким образом, 168 строк не исчезли и не превратились в 5. Семейное
разбиение в каждой из пяти складок использует 123–141 строку для обучения
и 27–45 для проверки, **если** все они будут надёжно размечены; всего
53 независимых семейства. Обученная на таком пилоте
модель и её «точность» были бы фикцией. Нужны более ранние и
разнотипные документы, проверяемый охват источников и согласованная
экспертная разметка; только затем запускать тренеры.

## 3. Модели и проверки

```bash
pip install -e '.[models]'
python -m lctrend.modeling train-catboost \
  --dataset artifacts/labels.csv --output-dir artifacts/models
python -m lctrend.modeling train-hgt \
  --dataset artifacts/labels.csv \
  --subgraphs artifacts/history.jsonl \
  --output-dir artifacts/models
```

Для годовой метки задайте `--target signal_12m`. Для пилотной семейной
проверки добавьте `--split family --fold 0` и повторите с `--fold 1`…`4`.
Для динамического когортного 80/10/10 используйте `--split cohort`.
Модели и отчёты разных горизонтов/складок сохраняются под разными именами.
По умолчанию остаётся строгая временная схема. Если в складке нет обоих
классов, обучение откажется запускаться; этот факт нельзя скрывать выбором
«удобной» складки.

Обе команды откажутся стартовать без согласованных положительных и
отрицательных примеров в `train` и `valid`, проверенного происхождения
меток, раздельных семейств и временного embargo. Защитный минимум пилота —
20 независимых семейств каждого класса в train и 10 в valid; на 53 семьях
этот порог для одной 5-кратной итерации недостижим. Это не
гарантия статистической достаточности и не метрика ТЗ. CatBoost получает
отобранные числовые признаки на дату T. Пропуски остаются пропусками,
а масштабные счётчики дополняются процентилями среди современников.
Вес каждой технологии нормируется, классы балансируются внутри эпох
только при обучении.

HGT использует два слоя, четыре головы внимания и четыре роли узлов:
технология, документ, организация и задача. Связи документа с технологией
имеют обратное направление для передачи сообщения к корню и возрастные
корзины (до года, 1–3 года, старше). У корня есть прямой табличный путь.
Вторая голова обучается только там, где есть метка будущего тренда.
Температура вероятностей подбирается на валидации. В JSON отчётах остаются
PR-AUC, ROC-AUC, Brier, ECE и размер частей. Без отложенного теста или
достаточного количества независимых сигналов не заявляем точность из ТЗ.

## 4. Объяснение конкретной оценки

```bash
python -m lctrend.modeling explain-catboost \
  --model-dir artifacts/models --dataset artifacts/labels.csv \
  --technology-id ID --snapshot 2021-01-01 \
  --output artifacts/explanations/example-catboost.json
python -m lctrend.modeling explain-hgt \
  --model-dir artifacts/models --subgraphs artifacts/history.jsonl \
  --technology-id ID --snapshot 2021-01-01 \
  --output artifacts/explanations/example-hgt.json
```

CatBoost сохраняет SHAP-вклады в логит и отдельно разницу в **процентных
пунктах вероятности** при замене одного признака на медиану обучающей
части. Например, для фактической высокой зрелости будет указано её
значение, базовая медиана и на сколько пунктов этот признак изменил
калиброванную вероятность. SHAP-числа сами по себе не являются
процентными пунктами. HGT сохраняет изменение вероятности при удалении
каждой ближайшей сущности и при такой же замене признака корня, включая
идентификатор, тип и дату документа. Сырые веса attention не выдаются за
объяснение: они не измеряют вклад в результат. Все эти изменения —
сравнения внутри модели, а не причинное влияние технологии или документа.

Выдача/GUI сможет показывать эти JSON только после проверки источников;
сейчас модели не включаются автоматически в поиск и не подменяют
существующий рейтинг. Это сохраняет требование ТЗ о проверяемости,
фильтрации зрелого рынка и информационного шума.
