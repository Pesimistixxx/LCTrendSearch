## 1. Резюме

**Общее состояние.** Инженерная основа сильная:
- 675 тестов за 5 с, от сети не зависят; `ruff check` без замечаний;
- аккуратные контракты: цитаты-доказательства, аудит `ProcessingRun`, атомарная запись;
- Cypher-инъекций нет, секреты не утекают в логи и результаты;
- путь признаков не подглядывает в будущее.

Но ключевой аналитический результат на реальных данных не получается:
- временной датасет для любого корпуса, который система собирает сама, пуст, а метки класса 0 невозможны;
- извлечение систематически теряет главную технологию документа;
- идентичность сущностей ненадёжна;
- ТОП-15 в интерфейсе — синтетика без пометки на экранах результатов.

**Главные риски:**
1. **Пустой датасет (E-1).** Документ «виден» только с даты скачивания: `max(published, retrieved)`. Все исторические срезы пусты, `build-training-set` даёт 0 строк. В текущем срезе любая технология выглядит «новой», ранжирование слабых сигналов переворачивается.
2. **Метка 0 недостижима (E-2).** Классификатор не обучить даже после исправления E-1.
3. **LLM-слой.** Теряет главную технологию (B-1), не рецензирует полнотекстовые пакеты (B-2), пропускает фантомные сущности (B-3).
4. **Идентичность (C-1…C-4).** AI, AM, IS, BE сводятся к одной лемме (Бельгия = Исландия = «ИИ»), русские падежи разделяются, дубль навсегда отключает имя, результат зависит от порядка документов.
5. **Демо-поиск (H-1).** Синтетика выдаётся за анализ, включая «цитаты» Gartner и OECD. PDF-экспорт вообще без пометки.

**Готовность к демо.** Сквозной путь «сбор → извлечение → Neo4j» и экран сбора работают: фронт собирается, контракт UI↔API совпадает. Показать «поиск слабых сигналов» пока честно нечем. До честного демо — примерно 2–3 человеко-дня (раздел 6).

## 3. Подробности

### 3.1 Critical

**E-1. Отсечка по времени сбора обнуляет историю**
- **Где.**
  - `src/lctrend/graph/temporal.py:101-108`: `available_date = max(version_date, retrieved_date)`.
  - `src/lctrend/graph/temporal.py:327-333`: упоминание видно с `max(observed, available_date, recorded)`, где `recorded = coalesce(m.recorded_at, run.started_at)` (`src/lctrend/graph/store.py:898`).
  - `retrieved_at` проставляется как `datetime.now()` (`src/lctrend/ingest/connectors.py:46-47`, `src/lctrend/ingest/file_adapters.py:794`).
- **Доказательство** (13 работ OpenAlex 2012–2024, настоящие адаптеры).
  - С реальными отметками времени `view(2016|2020|2025)` = [], `build-training-set` = **0 строк**.
  - С датами «как в тестах» — 24 строки.
  - Текущий срез: `first_seen=2026-09-27`, `age_days=2`, `documents_last_year=13/13`. По датам публикации было бы 2012-03-01, 5325 дней, 0.
  - Все временные фикстуры ставят `retrieved_at == published` (`tests/graph/test_temporal.py:14`, `tests/graph/test_dataset.py:28`, `tests/cli/test_cli_dataset.py:61`), поэтому тесты зелёные.
- **Последствия.** Обучающей выборки нет. Во входе будущего ТОП-15 устоявшиеся технологии выглядят максимально новыми.
- **Оценка решения.** Оно осознанное (тест `test_publication_does_not_backdate_a_later_retrieval`), но для ретроспективы не обосновано. Содержимое статьи 2019 года известно с 2019 года; «время знания» нужно только для изменяемого: метрик и участников.
- **Как исправить:**
  ```python
  @property
  def available_date(self) -> date:
      return self.version_date                    # содержимое — по публикации
  available = max(observed, version.available_date)  # без recorded
  ```
  - Метрики оставить на `metrics_observed_at` — так уже сделано.
  - Строгий режим вынести в опцию `--as-known`.
  - Добавить фикстуру «собрано в 2026».
  - В ограничениях описать смещение отбора запросами 2026 года.

**E-2. Метка 0 недостижима — датасет одноклассовый**
- **Три независимых блока:**
  1. В `covered_families` (`src/lctrend/graph/temporal.py:510-533`) при `cutoff = period_end = horizon_end` обход отбрасывается и при `observed > cutoff`, и при `observed < period_end`. Проходит только обход, завершённый ровно в день `horizon_end`. Вызов — `src/lctrend/graph/training.py:626-631`.
  2. `src/lctrend/cli.py:254` всегда пишет `"exhaustive": False`, веб-обход CrawlRun не пишет вовсе.

> **Решение после аудита:** логику получения ответа (отбор кандидатов, скоринг, объяснение, ТОП-15, бэктест) пока не делаем. Подготовленный функционал вынесен в [src/lctrend/ranking/](../src/lctrend/ranking/README.md); пункты ниже и шаги 8–9 плана описывают заготовку, а не готовый результат.

**Минимальная форма «красных» блоков:**
- **Отбор кандидатов.** Правила на дату T: Technology или Method, не generic, ≥2 независимых источника за 24 месяца, возраст ≤3–5 лет, стадия не выше pilot.
- **«Классификатор».** Пока метки одноклассовые — прозрачный взвешенный скор по z-нормированным признакам: рост, ускорение, разнообразие и независимость источников, новизна, прогресс зрелости, штраф за уже коммерческие. Вклад признака = вес × значение, SHAP не нужен. После исправления E-2 — логистическая регрессия на walk-forward.
- **Объяснение.** Топ-3 вклада признаков плюс 2–3 цитаты из accepted-утверждений (документ, дата, URL). Они уже лежат в графе, и это сильный аргумент на защите.
- **ТОП-15.** `/api/search` в контракте `api.js`, `VITE_MOCK=0` в Docker-сборке.
- **Метрика для питча.** Бэктест «ТОП-15 на 2021 год → рост в 2021–2023» против случайной выборки: precision@15.
- **GNN/HGT и экспорт подграфов** до защиты не трогать.
