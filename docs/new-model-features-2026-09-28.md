# Новые фичи для LCTrendSearch: признаки технологии для модели

Дата: 28 сентября 2026. Документ исправляет первоначальную трактовку запроса: здесь **входные признаки технологии на дату T**, которые можно добавить в feature builder, обучающий набор и рейтинг. Приведены **15 новых семейств фичей**. Это предложения, сверенные с текущим кодом; они ещё не реализованы и их полезность на нашем корпусе не измерена. Все численные примеры иллюстративные.

Единица строки — `technology × snapshot`. Для признаков применения нужна более точная единица `technology × application × snapshot`: одна технология может быть зрелой в одной задаче и новой в другой. Такой ключ потребует расширения нынешнего датасета и отбора кандидатов. Несколько приложений нельзя молча объединять в одну строку.

Порядок работ и зависимости — в [плане дополнений](implementation-roadmap-2026-09-28.md).

## Что уже существует и не считается новой фичей

В `src/lctrend/graph/features.py` уже есть рост/ускорение/burst/persistence, возраст, концентрация и разнообразие, независимость, новые участники, source convergence, paper→artifact/company lags, длина evidence chain, supported/speculative/negated ratios, attention–evidence gap, гранты/вакансии/зарплаты, зрелость/TRL, релизы/коммиты/contributors, стандарты и coverage.

В `src/lctrend/graph/novelty.py` уже есть semantic novelty, name-vector distances/outliers, branch novelty, centralities и их изменение, structural holes, bridge, новые domain pairs, recombination и task novelty. В `training.py` уже добавляются new relations, missingness и snapshot percentiles денежных/трудовых значений.

Все эти семейства участвуют в общем builder. Только семь полей имеют веса в стандартном `ranking.json`; отсутствие веса **не означает отсутствия фичи**. OpenAlex references/FWCI и GitHub license/fork metadata также уже сохраняются: новые фичи ниже используют другую логику поверх них или требуют нового сбора.

## Общий контракт входных признаков

1. Фича использует только события и версии, доступные к T. Будущие реализации остаются labels/outcomes. Исторический replay и строгий `as_known` различаются явно.
2. Для каждой группы полей сохраняются support count, coverage, missing reason, версия определения, окно и evidence IDs. Они могут быть отдельными predictor/metadata columns по утверждённой схеме.
3. `None` — измерение невозможно или наблюдение неполно; 0 — корректно измеренное отсутствие события. Непубличный результат и неуспешный поиск не дают подтверждённый ноль.
4. Источники дедуплицируются по происхождению: PR-копии, ownership, авторы и проекты. Unknown ownership не означает независимость.
5. Сначала сохранять признаки по сопоставимому application/benchmark slot. Агрегация в technology row фиксируется заранее и сохраняет counts/покрытие; нельзя выбирать самое выгодное применение после просмотра результата.
6. «Больше» не всегда «лучше». Много внедрений может означать зрелость, а большое изменение контекста — смену словаря. Направление влияния проверяется для выбранного target; правила зрелости сохраняются.
7. Масштабы, smoothing, пороги и embedding/model versions фиксируются на разрешённой истории, без настройки по закрытому тесту.
8. Все численные predictors конечны. Формулы с `ln(x/y)` допустимы только для конечных строго положительных x/y и ratio-пригодной шкалы; иначе другая заранее заданная metric-specific формула либо `None + reason`, без произвольного epsilon.

## F01. Рост доли технологии сверх общего фона

**Поля:** `exposure_adjusted_growth_12m`, `excess_growth_probability_12m`, `growth_rate_ratio_lower_bound`, `growth_exposure_coverage`.

**Смысл.** Если технология выросла с 5 до 20 наблюдений, а сопоставимый корпус — с 1000 до 4000, её raw-доля осталась .005. Обычный growth видит увеличение числителя; новая фича оценивает интенсивность относительно общего фона.

Для каждой фиксированной ячейки `source family × area × collection policy` взять непересекающиеся previous/recent окна: y — дедуплицированные наблюдения технологии, E — объём сопоставимого фонового корпуса, независимо от запроса технологии.

```text
adjusted_growth = ln((y_recent + α) / (E_recent + β))
                  − ln((y_previous + α) / (E_previous + β))
y_w ~ Poisson(E_w × λ_w)
λ_w ~ Gamma(α, β)                         # shape–rate
λ_w | data ~ Gamma(α + y_w, β + E_w)
excess_probability = P(λ_recent > (1 + δ) × λ_previous | data ≤ T)
```

α, β и минимально существенный рост δ — параметры версии, не универсальные константы. В первом поле используется логарифм отношения posterior mean intensities; неопределённость оценивается отдельно. Нижняя граница rate ratio зависит от зафиксированного уровня интервала. Для технологии с несколькими ячейками сохранять отдельные значения либо заранее заданный сопоставимый агрегат с фиксированными весами.

**Данные:** новый слой totals/exposure и история coverage. Собственный тематический TOP-N не является общим фоном. При E=0 или несовместимых политиках — `None`; при overdispersion проверять другую count-модель.

**Отличие:** существующие growth и snapshot percentile не нормируют наблюдения на отдельный фон источника/области. Увеличение y и E одновременно не должно изображать четырёхкратный технологический прорыв, хотя uncertainty изменится.

Poisson–Gamma — опубликованный стандартный метод; использование для technological exposure — наша адаптация. [Stan: posterior prediction](https://mc-stan.org/docs/stan-users-guide/posterior-prediction.html).

## F02. Новые независимые внешние пользователи

**Поля:** `new_external_adopter_groups_12m`, `external_adopter_entry_rate_12m`, `external_use_evidence_count`, `external_adopter_identity_coverage`.

**Смысл.** Важен приход тех, кто начал использовать результат, не участвуя в его разработке. Упоминание новой компании в статье ещё не означает adoption.

```text
new_external_adopter_groups_12m = количество actor-groups,
  чей первый подтверждённый use для technology × application попал в (T−12м,T]
  и которые не входят в developer/owner group этого результата
entry_rate = новые группы с первым use в пригодных месяцах наблюдения
             / количество этих пригодных месяцев
```

**Пример.** Пять публикаций разработчика не добавляют внешних пользователей. Два независимых actor-groups с проверенными кейсами использования дают count=2, если ранее они не были пользователями в наблюдаемой истории.

**Данные:** first-use events, actor/application/project, developer identity и ownership на T. Если начало наблюдения позднее первого возможного использования, это «первое наблюдаемое», а не гарантированно первое реальное; хранить соответствующий флаг и не смешивать показатели. Numerator rate включает только события тех же пригодных месяцев, которые входят в denominator; общий наблюдаемый count за 12 месяцев сохраняется отдельно. Если пригодных месяцев нет, rate=`None`.

**Отличие:** `commercial_user_count` считает пользователей, `new_company_count` — компании в документах. Ни одно не выделяет датированный вход внешнего независимого пользователя. Совместные авторы, грант или план пилота не дают use event.

**Приёмка:** self-use, subsidiaries и повторные сообщения не создают новых внешних групп; неизвестная ownership остаётся неизвестной. Для ранних сигналов отдельно различать external pilot и commercial deployment.

## F03. Повторное применение после первого пилота

**Поля:** `repeat_use_conversion_12m`, `repeat_use_success_count`, `repeat_use_eligible_cohort_count`, `repeat_use_followup_coverage`.

**Смысл.** Продление, второй объект или расширение применения показывает продолжение после первой демонстрации.

Единица — первая пилотная когорта `technology × application × actor-group`. Проекты/площадки — события продолжения. Для версии с H=12м:

```text
eligible = когорты с first_pilot_at + H ≤ T и достаточным follow-up
conversion = когорты с подтверждённым repeat/renewal/expansion в (p,p+H] / eligible
```

**Пример.** Из пяти полностью наблюдаемых когорт три получили подтверждённое продолжение: .6 при n=5. Поле остаётся историческим predictor на T: оно не использует будущие продолжения молодых пилотов.

**Данные:** связанные пилот/продление, даты, actor/application, event type и первичное evidence. Follow-up policy фиксирует источники, окна, aliases/projects, успешность сбора и пробелы до расчёта; не выбирать eligible только среди успехов.

**Отличие:** maturity rank и user count не связывают повторные события конкретной когорты. Новая версия репозитория и повторный пресс-релиз не являются повторным применением.

**Ограничение:** это наблюдаемая конверсия в заявленном контуре. Публичное молчание не доказывает отказ; неполные когорты — `None`/неоценимы. Молодые когорты не являются отрицательными. Коммерческая зрелость может сделать объект неподходящим для weak-signal target — это проверяется отдельно.

## F04. Подтверждённый перенос в новые отрасли

**Поля:** `new_verified_industry_count_12m`, `verified_industry_transfer_strength_12m`, `independent_industry_use_count`, `industry_assignment_coverage`.

Пусть A(T) — отрасли конкретных подтверждённых use events. Для нового сектора a, отсутствовавшего в A(T−12м), U(a) — независимые внешние actor-groups с использованием.

```text
new_industry_count = |A(T) \ A(T−12м)|
transfer_strength = Σ_new_a ln(1 + U(a)) × distance(a, A(T−12м))
```

**Смысл/пример.** Упоминание медицины и энергетики в одной статье не меняет поле. Реальный новый кейс применения в энергетике добавляет отрасль.

**Данные:** датированные actor/application события, отраслевой справочник и фиксированная distance policy. При пустом исходном A учитывать первое применение отдельно, без искусственного максимального расстояния. Базовый count можно внедрить без distance.

**Отличие:** domain entropy/new domain pairs/task novelty описывают связи и сочетания. Эта фича требует использования. Отрасли холдинга целиком не наследуются одному подразделению автоматически.

**Ограничение:** это индекс наблюдаемого переноса, не доля мирового рынка; emerging application не отменяет зрелость старого массового применения.

## F05. Конфликт сопоставимых независимых результатов

**Поля:** `independent_claim_conflict_strength`, `independent_refutation_share`, `critical_conflict_slot_count`, `comparable_claim_slot_count`, `mixed_origin_group_count`.

Слот: technology/application + metric/unit + baseline + dataset/workload/conditions + version + event interval. P и N — **количества непересекающихся** независимых групп с поддерживающим и опровергающим итогом в этом слоте.

```text
conflict_slot = 2 × min(P, N) / (P + N)
refutation_share_slot = N / (P + N)
```

Mixed-группа с внутренним support/refute показывается отдельно и не входит одновременно в P и N. Для technology aggregate фиксировать максимум/распределение conflict и support counts; один критический конфликт не скрывать средним. «Критический» slot задаётся до оценки в каталоге требований, а не по удобному результату.

**Пример.** 2 support / 2 refute дают conflict=1. При 0/4 conflict=0, но refutation_share=1: проверки согласуются в отрицательном результате. Поэтому оба поля нужны вместе.

**Данные:** полный Assertion export, values/conditions/polarity, canonical claim matching и review сопоставимости. `verification_status=supported` означает опору извлечения на текст, а не доказанную истинность научного результата.

**Отличие:** `negated_claim_ratio` — доля отрицаний, без сопоставления результата и условий. Разные температуры/версии/интервалы не создают конфликт автоматически. При отсутствии сопоставимых групп — `None`.

Формула предложена для проекта. Научная связь support/refute/evidence: [SciFact, Wadden et al., EMNLP 2020](https://aclanthology.org/2020.emnlp-main.609/); формула не приписывается SciFact.

## F06. Величина независимо воспроизведённого выигрыша

**Поля:** `replicated_gain_median`, `replicated_gain_lower_bound`, `confirmed_replication_share`, `independent_test_coverage`, `replication_group_count` — по фиксированным benchmark slots.

```text
gain_j = direction × ln(value_new_j / value_baseline_j)
direction = +1 для «больше лучше», −1 для «меньше лучше»
confirmed_share = claims с подтверждённым выигрышем / claims с оценимой независимой проверкой
test_coverage = claims с независимым сопоставимым измерением / пригодные исходные claims
```

**Пример.** Энергия 30→15 при одинаковой задаче даёт −ln(.5)≈.693. Throughput 100→200 даёт ln(2)≈.693, но это другой slot: их нельзя объединять как один benchmark.

**Данные:** metric/unit/direction, baseline, workload/hardware/dataset/version, uncertainty и origin group. Подтверждение требует воспроизведения направления и величины в заранее выбранных пределах. Для median сначала агрегировать повторные измерения одной origin-group внутри slot по фиксированному правилу, затем дать группам равный вес. `replicated_gain_lower_bound` — нижняя доверительная граница именно медианного group-level gain, а не минимальное наблюдение/нижний квантиль отдельных результатов. Уровень и метод интервала фиксируются до оценки; resampling/uncertainty учитывают независимые origin-groups и зависимость измерений внутри группы. При недостаточной поддержке метода — `None`. Используются заранее выбранный benchmark и все пригодные независимые результаты; выбирать только успешные проверки для величины эффекта нельзя. Отдельно хранить число подтверждённых репликаций.

Опровергнутая проверка входит в denominator confirmed_share и не входит в numerator. Неопределённые/смешанные итоги, непроверенные claims и coverage показываются отдельно; правило итогового verdict по всем проверкам фиксируется заранее. Цитирование старого числа — не replication.

**Отличие:** `performance_gain_evidence` сейчас считает claims о changes_metric, не величину и воспроизводимость выигрыша. Для accuracy нужны percentage points; для нулевых/отрицательных значений или нерелятивных шкал использовать другую объявленную формулу либо `None`, без произвольного epsilon. Нижняя граница без достаточных независимых измерений не выдумывается.

## F07. Связная передача результата и устойчивость её оснований

**Поля:** `validated_transfer_depth`, `independent_downstream_path_count`, `min_origin_claim_survival`, `transfer_link_coverage`.

**Смысл.** Научная работа → реализация метода → испытание → внешний application — только при доказанном переходе между конкретными объектами. Патент и публичный код не обязательны: допустим прямой научно-прикладной переход с явным evidence.

```text
depth = максимальное число проверенных переходов простого, согласованного по времени пути
downstream_count = число независимых actor/application применений с таким путём
origin_claim_survival = min_g (подтверждённые critical downstream slots после удаления g
                              / подтверждённые critical downstream slots до удаления)
```

Каждое ребро требует идентификации объектов **и** доказательства «реализовал/использовал/перенёс». Общий автор, проект ID, citation или хронология сами по себе переход не доказывают. Пути одного downstream actor/project объединяются, циклы не увеличивают depth.

**Данные:** work/artifact/project IDs, application/actor, dates, evidence каждого ребра и origin masks. Для survival заранее определить критические downstream claim slots конкретного применения. Удалить подтверждения одной поддерживающей origin-group, сохранив IDs/identity mapping; проверить, остаются ли claims подтверждёнными другими независимыми основаниями. При пустом исходном наборе — `None`. Удаление общей исходной статьи не должно механически обнулять все downstream claims только из-за пропавшей вершины: здесь оценивается опора конкретных утверждений, а не наличие названия в графе. Низкая сохранность означает зависимость evidence, не доказательство ложности.

**Отличие:** `evidence_chain_length` считает типы документов после первой статьи. Новые поля требуют конкретной связи и не зависят от предсказания модели, поэтому не создают цикл «score становится собственным входом».

## F08. Смена контекста фактического применения

**Поля:** `application_context_shift_12m`, `new_application_context_cluster_count`, `application_context_group_support`, `application_context_coverage`.

**Смысл.** Название технологии остаётся прежним, но фактические применения меняются. Например, метод из одной задачи переносится в другое применение с подтверждённым use, а не только новым ключевым словом.

```text
shift = 1 − cosine(centroid(confirmed application contexts in recent 12м),
                   centroid(confirmed application contexts in previous 12м))
```

**Данные:** датированные application/evidence spans, фиксированная embedding space и дедуплицированные contexts. Каждый context связан с подтверждённым use этой технологии, actor/application и событием, а не просто тематическим упоминанием. Вес задавать по независимым группам, а не числу перепечаток; сохранять поддержку обеих эпох. Context clusters строятся по одной зафиксированной методике, без knowledge будущих периодов; считать новые подтверждённые кластеры по появлению на T.

**Отличие:** существующая semantic novelty сравнивает name vectors с другими концептами/текущим кластером. Task novelty оценивает сочетания задач. Здесь сравниваются содержательные application contexts одной технологии между периодами.

**Ограничение:** смена языка, стиля источника, embedding version или состава сборщиков может имитировать shift. При недостаточной/несопоставимой поддержке или нулевой норме centroid — `None`; показывать изменившиеся кейсы. Большая cosine distance сама по себе не означает хороший сигнал.

## F09. Внешние проекты, действительно зависящие от реализации

**Поля:** `independent_downstream_dependency_groups`, `new_downstream_dependency_groups_12m`, `direct_dependency_context_count`, `dependency_observation_coverage`.

**Смысл.** Звёзды и forks выражают интерес. Явное подключение библиотеки/артефакта в независимом проекте — другой наблюдаемый факт.

```text
dependency_groups = независимые внешние project/owner groups
  с прямой versioned dependency на канонический артефакт технологии, доступной к T
new_groups_12m = группы с первым наблюдаемым подключением в (T−12м,T]
```

**Данные:** dependency/lock/build manifests на зафиксированных commits, package/artifact identity, timestamps и ownership. В нынешних нормализованных PyPI metadata нет `requires_dist`; `requires_python` — версия интерпретатора, а не список downstream потребителей. Нужны новый вход manifests и reverse-dependency слой. Разделять runtime/build/dev/example зависимости. Forks, tutorials и generated manifests не выдавать за production use. Собирать только доказанную связь артефакта с технологией; библиотека общего назначения не передаёт всем зависимым проектам каждую упомянутую в README технологию.

**Отличие:** implementation/release/commit/contributor counts уже есть; count внешних зависимых проектов отсутствует. GitHub fork/license metadata уже сохранены, но нужны новый сбор и разбор manifests.

**Ограничение:** это adoption в видимой части software ecosystem. Dependency не доказывает успешное промышленное использование; скрытые проекты и неполный индекс дают coverage, не ноль мирового adoption.

## F10. Запас до требований практической применимости

**Поля:** `practical_threshold_margin`, `critical_requirement_pass_count`, `requirement_measurement_coverage`, `fully_assessed_requirement_set`.

**Смысл.** Улучшение вдвое может всё ещё быть непригодным, если требуемый результат на порядок выше. Нужен конкретный target application с известными требованиями.

Для каждого обязательного условия j в одном сопоставимом сценарии:

```text
margin_j = direction_j × ln(measured_value_j / required_threshold_j)
practical_threshold_margin = min_j margin_j
```

Положительное margin означает выполнение соответствующего ограничения. Минимум отражает самое слабое обязательное условие. Он рассчитывается как общий margin только при полном наборе обязательных измерений; иначе partial margins + coverage и `None` для полного результата.

**Пример.** Требуется энергия ≤20 единиц на задачу, измерено 30: −ln(30/20)≈−.405. Улучшение относительно старого метода может быть реальным, но это условие ещё не выполнено.

**Данные:** требования конкретного применения, источник/дата их знания, metric/unit/direction, сопоставимый workload и подтверждённые measurements. Thresholds нельзя выбирать по будущему победителю. Разные обязательные метрики должны относиться к одному валидному сценарию/конфигурации; набор лучших чисел от разных несовместимых конфигураций не создаёт «готовность».

**Отличие:** TRL/maturity описывают стадию, performance_gain_evidence — наличие утверждения об улучшении. Здесь измеряется расстояние до практического условия. Measured value и threshold должны быть конечными строго положительными числами; для нулевых/отрицательных значений и нерелятивных шкал — отдельное заранее заданное определение либо `None`, не эта ratio-формула.

## F11. Снятие критических технических барьеров

**Поля:** `unresolved_critical_blocker_count`, `resolved_critical_blocker_share`, `new_blocker_resolutions_12m`, `days_since_last_critical_resolution`, `blocker_status_coverage`.

**Смысл.** Реализации мог мешать конкретный материал, производственный процесс, вычислительный ресурс, датасет или разрешение. Датированное подтверждение снятия препятствия меняет возможность применения раньше массового adoption.

```text
resolved_share = подтверждённо снятые blockers / blockers с оценимым текущим статусом
new_resolutions_12m = независимые resolution events в (T−12м,T]
```

**Данные:** `technology × application` requirement/blocker, обязательность, зависимости, проверенные status transitions и availability. Само наличие связанного материала/оборудования не означает снятие барьера: нужны достаточные характеристики и связь с выбранным сценарием. Нужны расширение extraction-контракта и событийный экспорт.

**Отличие:** bridge/structural holes относятся к графу тем; TRL — к стадии. Они не выражают конкретное обязательное препятствие и его разрешение.

**Ограничение:** перечень blockers может быть неполным. Считать 100% готовности при неизвестных обязательных статусах нельзя; показывать unknown count. Обязательные условия соединяются AND, допустимые альтернативы — OR. Смена задачи или ослабление требования не является снятием исходного барьера. Снятие одного барьера не гарантирует успеха и не является причинным доказательством реализации.

## F12. Выполнение датированных технических обещаний

**Поля:** `technical_promise_fulfillment_share`, `fulfilled_promise_count`, `missed_or_withdrawn_promise_count`, `promise_result_followup_coverage`, `promise_deadline_delay_median_days`.

**Смысл.** Доля speculative claims уже есть. Новая фича связывает конкретное прежнее обещание с проверенным результатом после наступления объявленного срока.

```text
eligible = обещания с заранее известным deadline ≤ T и оценимым итогом
fulfillment_share = eligible с подтверждённым выполнением в срок / eligible
delay_days = actual_confirmed_completion_at − original_deadline
```

**Данные:** исходная version обещания, actor/project, measurable milestone, deadline, условия и связанные fulfillment/withdrawal/failure events. Обещание должно быть доступно до deadline; поздняя ретроспективная фраза не создаёт историческое обещание. Неточная дата вроде «в 2026 году» задаёт интервал: overdue определяется после его верхней границы. Новая дата после переноса не затирает старую. Delay рассчитывается только при известной completion date; незавершённые/неоценимые обещания показываются отдельно.

**Отличие:** speculative/factual ratio не проверяет, сбылось ли прежнее обещание. Generic «скоро изменим рынок» без измеримого milestone/deadline не участвует.

**Ограничение:** молчание после срока не доказывает провал. Eligible не выбирается только по успешным сообщениям; нужны отрицательные первичные сведения либо достаточный наблюдаемый follow-up по объявленной методике. Признак характеризует подтверждённую историю проекта, не переносится автоматически на все технологии разработчика.

## F13. Сохранение эффекта при переходе lab→pilot

**Поля:** `scaleup_gain_delta`, `scaleup_critical_metric_delta`, `verified_scaleup_pair_count`, `scaleup_comparison_coverage`.

**Смысл.** Лабораторное преимущество может исчезнуть при большем объёме, реальном сырье или эксплуатационных ограничениях. Сам факт стадии pilot этого не показывает.

Для связанной пары результатов одного метода/версии и сопоставимой задачи, с явно указанным изменением масштаба:

```text
scaleup_delta_j = direction_j × ln(normalized_pilot_value_j / normalized_lab_value_j)
```

Положительное значение — улучшение по данной метрике при переходе; отрицательное — деградация. Для catalogued критических метрик сохранять слабейший результат и полный набор пар, не только удачные переходы. Lab/pilot значения должны быть конечными строго положительными; для нулей/отрицательных значений и нерелятивных шкал применять объявленную разность/иной валидный показатель либо `None`, без epsilon.

**Пример.** Энергия на единицу одинаковой работы выросла с 30 до 45: delta=−ln(1.5)≈−.405. Увеличенный общий объём без нормировки на выполненную работу не считается ухудшением энергоэффективности.

**Данные:** доказанная связь lab/pilot, единицы, workload/baseline/условия, масштаб и uncertainty. Изменение условий допускается только по заранее определённым scale-up осям и учитывается явно; несвязанные benchmark numbers не образуют пару. Все результаты доступны к T.

**Отличие:** maturity/time-to-pilot измеряют событие/срок, F06 — независимое воспроизведение в сопоставимых условиях. F13 измеряет устойчивость эффекта к конкретному расширению масштаба и реальных условий. Отсутствие пилота даёт `None`, а не «провал масштабирования».

## F14. Citation disruption на дату T

**Поля:** `citation_disruption_age_field_adjusted`, `citation_disruption_supported_work_count`, `citation_closure_coverage`.

Для focal work f: Nf — последующие работы, цитирующие f без его references; Nb — цитирующие f и хотя бы один reference; Nr — цитирующие references без f. Используются только работы/связи, доступные к T.

```text
CD(T) = (Nf − Nb) / (Nf + Nb + Nr)
```

**Смысл.** Изменение траектории научного продолжения. CD лежит в −1…1 и не является вероятностью коммерческого успеха. Нулевой denominator даёт `None`.

**Данные:** citing-work expansion, направленные citation edges и availability, bibliography coverage. References уже сохраняются; citation closure и feature computation нужны отдельно. Агрегат работ технологии и age/field peer correction фиксируются заранее; latest lifetime counters не становятся историческими predictors.

**Отличие:** нынешний technology graph — co-mentions/relations, не сеть цитирования. Citations count/FWCI не измеряют CD.

Опубликованная метрика: [Funk & Owen-Smith, Management Science](https://pubsonline.informs.org/doi/abs/10.1287/mnsc.2015.2366). Пустая библиография API не даёт автоматически CD=1: артефакты отсутствующих references существенно влияют на оценку. [Holst et al., Nature 2026](https://www.nature.com/articles/s41586-026-10787-y). Сравнивать одинаковый возраст работ и полноту данных.

## F15. Старое научное знание с новым подтверждённым применением

**Поля:** `science_revival_beauty_percentile`, `new_verified_transfer_from_old_work_count_12m`, `science_revival_transfer_score`, `revival_link_coverage`.

Для конкретной работы c_t — годовые цитирования после публикации, t_m — первый максимум в истории, доступной к T:

```text
line_t = c_0 + (c_tm − c_0) × t / t_m
B(T) = Σ_t=0..tm (line_t − c_t) / max(1, c_t)
при t_m = 0: B = 0
revival_score = percentile(B in age/field cohort at T)
                × ln(1 + new_verified_external_transfer_count_12m)
```

Beauty coefficient описывает delayed scientific recognition: [Ke et al., PNAS 2015](https://pmc.ncbi.nlm.nih.gov/articles/PMC4475978/). Выбор первого из равных максимумов — правило версии нашей реализации. Итоговый revival_score — наша дополнительная формула, не коэффициент из статьи.

**Смысл.** Высокое позднее признание дополняется фактом переноса старого конкретного результата в новый application. Старый возраст технологии не переименовывается в «новую технологию».

**Данные:** work identity, годовая citation history, прямые transfer evidence и независимые actor/application events. Yearly history уже частично сохраняется; missing years не заполняются нулями без основания. Пик только прошлый относительно T; текущий неполный год не объявляется полным. Если история/связь непригодна, соответствующее поле — `None`.

**Отличие:** возраст, task/domain novelty не подтверждают delayed recognition и прямой перенос. Нужен отдельный scenario `technology × new application`: текущий возрастной gate может исключить такие случаи. Пересмотр gate делается явно и проверяется на зрелых массовых технологиях.
